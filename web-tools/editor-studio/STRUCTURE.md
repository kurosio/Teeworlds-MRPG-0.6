# Editor Studio — структура и ядро

Этот пакет содержит **единое ядро UI + DB** и несколько редакторов, подключаемых как независимые страницы.

## 1) Корень проекта

- **index.html** — *Editor Studio*: оболочка (адаптивная) переключает iframe на нужный редактор.
  Оформление оболочки (сайдбар, пункт меню `.studio-item`, шапка рабочей области, экран
  входа) собрано на тех же токенах, что и вкладки, поэтому переход между меню и
  редактором не выглядит переходом в другое приложение.
- **studio.manifest.js** — список редакторов Studio, сгруппированных по категориям (файлы / БД / система).
- **scenario-editor.html** — редактор сценариев.
- **settings.html** — вкладка настроек (подключение к БД + просмотр источников списков + настройка синхронизации).
- **database.html** — вкладка управления БД (подключение, дампы, восстановление).
- **vouchers-editor.html** — редактор ваучеров (CRUD напрямую в БД, использует ядро).
- **bots-info-editor.html** — редактор ботов (tw_bots_info).
- **bots-npc-editor.html** — редактор NPC (tw_bots_npc).
- **worlds-editor.html** — редактор миров (tw_worlds).
- **aethers-editor.html** — редактор телепортов Aethers (tw_aethers).
- **change-requests.html** — запросы на изменение: для гостя — черновик + отправка + «Мои запросы», для администратора — очередь, просмотр, принятие/отклонение, общие лимиты гостевого доступа.
- **guests-editor.html** — гостевые пользователи (только администратор): создание аккаунтов, пароли, включение/выключение и набор доступных вкладок для каждого гостя.
- **api.php** — файловый API для сценариев (список/загрузка/сохранение JSON в `scenarios/`). Только администратор.
- **api/db.php** — безопасный DB API (конфиг + справочники для DB Select).
- **api/db-core.php** — общие helper-функции для DB API (конфиг + подключение).
- **api/db-maintenance.php** — API для дампов/восстановления БД.
- **api/db-crud.php** — универсальный CRUD API для DB-редакторов (ресурсы описываются в карте на сервере).
- **api/db-sync.php** — API для синхронизации между БД (сравнение схем, применение операций).
- **api/auth.php** — вход администратора/гостя (личный логин + пароль гостевого аккаунта), статус сессии, выход.
- **api/guests.php** — управление гостевыми аккаунтами (только администратор): list/create/update/password/revoke/delete.
- **api/db-resources.php** — общая карта ресурсов (таблицы, колонки, ссылки, обратные FK, доступность для гостя).
- **api/change-requests.php** + **api/change-requests-lib.php** — API запросов гостей (проверка, анализ влияния, конфликты, применение одной транзакцией, переписка гость ↔ администратор).
- **api/map.php** — карта мира и её текстуры для окна «Местоположение»: отдаёт
  `maps/<tw_worlds.Path>` и `data/mapres/*.png` (только чтение, только своим).
- **vendor/ddnet-map/** — локальный рендер карт DDNet (`twwebgl.js`, `twdatafile.js`,
  `picker.html/css/js`). Карта рисуется в браузере без интернета; лицензии и
  список изменений — в `vendor/ddnet-map/NOTICE.md`.
- **api/store.php** — хранилище Editor Studio на SQLite: настройки, гостевые аккаунты, счётчики попыток входа, лимиты частоты, запросы на изменение и переписка. Все данные редактора живут в одном файле `data/editor-studio.sqlite`.

### Быстрая проверка перед отправкой

```bash
node web-tools/editor-studio/tools/check.mjs
```

Скрипт без зависимостей проверяет синтаксис всех страниц и модулей, следит, чтобы
не вернулись убранные приёмы (прямой `fetch`, нативный `confirm`, захардкоженная
локаль дат), и показывает строки интерфейса без английского перевода.

## 2) editor-core/ — единый набор UI-компонентов и утилит

### Инициализация
- **bootstrap.js** — единая точка входа для редакторов: подключает тему, toasts, запускает UI Manager.
- **ui-manager.js** — *Core UI Manager*: 
  - автозагрузка `DB Select` (`EditorCore.DB.init()`),
  - validation hints (`data-validate`),
  - синхронизация Toggle (`data-checked`).

### Компоненты и рендеринг полей
- **field-renderer.js** — рендерит поля по JSON-схеме:
  - Input (text/number/password)
  - Textarea
  - Select / Multiselect
  - Date / Time / Datetime
  - Checkbox / Toggle
  - Modal (через `ui.js`)
  - DB Select / DB Multiselect (`type: db_select`, `db_multiselect`)

### Схемы и конфигурация
- **registry.js** — библиотека схем (JSON-конфиги полей/компонентов/действий). Здесь заменены ID-поля на DB Select (quests/items/worlds/bots).
- **defaults.js** — дефолтные стили/параметры для форм и модалок.

### UI и утилиты
- **ui.js** — модальные окна, toasts, базовые UI-хелперы + Tabs/Table (не завязаны на конкретный редактор).
- **utils.js** — общие функции (toasts контейнер, helper’ы): экранирование, `qs`, `debounce`,
  `setStatus`, `Dirty`, загрузка файлов и JSON-запросы (`fetchJson`/`requestJson`).
- **http.js** — единственный сетевой слой: `EditorCore.Http.json(url, options)` и
  `Http.request()` (то же, но бросает исключение), `Http.text()`. Внутри — таймаут
  (15 с по умолчанию), отмена через `AbortSignal`, разбор ответа с «мусором» перед
  JSON, единый результат `{ ok, status, error, data }` и сообщение оболочке на 401.
  Страницы и модули не вызывают `fetch` напрямую — так у всех запросов одинаковые
  таймаут, обработка ошибок и реакция на истёкшую сессию.
- **page-kit.js** — то, что нужно каждой странице: `EditorCore.Page` с `esc`, `t`
  (перевод), `locale`, `fmtDate`, `plural`, `toast`, `debounce`, `api`, `withBusy`,
  `confirm`/`alert` (общий модальный диалог вместо нативного `confirm()` с
  переводом кнопок), `report` (журнал неожиданных ошибок).
- **core.js** — базовая инициализация EditorCore.

### DB слой
- **db.js** — клиент к `api/db.php` + кеширование + автозаполнение `<select data-datasource="...">`.
- **db-crud.js** — клиент к `api/db-crud.php` (list/get/create/update/delete) для DB-редакторов. Автоматически записывает операции для синхронизации.
- **db-sync.js** — модуль синхронизации между БД: история изменений, проверка схем, применение операций, UI.
- **guest-mode.js** — гостевой режим (`EditorCore.Guest`): роль и аккаунт, черновик запроса в localStorage (по каждому гостевому аккаунту отдельно), наложение черновика и отправленных запросов на данные БД, блокировка недоступных вкладок, плашка гостя.
- **i18n.js** — переключение языка интерфейса RU/EN: `EditorCore.I18n` (`t`, `set`, `toggle`, `locale`, `plural`, `onChange`). Переводит разметку, атрибуты (`title`, `placeholder`, `aria-label`), динамически добавленные узлы (наблюдатель за DOM) и нативные `alert/confirm`; выбор языка хранится в `localStorage` (`editorStudio.lang`) и переключатель есть в шапке каждой вкладки.
- **i18n-en.js** — английский каталог: ключ — русская строка в том виде, в каком она отрисована, значение — английский текст (см. раздел 9).

### Упрощение создания редакторов
- **page-loader.js** — подключает тему, шрифты, Tailwind и файлы ядра одним тегом
  (`<script src="editor-core/page-loader.js">`); если CDN недоступен, один раз предупреждает
  об этом, вместо того чтобы оставить страницу без оформления.
- **form-runtime.js** — минимальный schema-runtime: 2-way binding, list add/remove, переиспользуемый в новых редакторах.
- **db-editor-runtime.js** — компактный runtime для CRUD-редакторов БД (список + форма + сохранение).
- **help.js** — кнопка «?» в шапке каждого редактора: короткая инструкция по вкладке
  (порядок работы, смысл полей, правила для гостя) и общий `Ctrl+S`.

### Тема
- **editor-theme.css** — единые CSS variables + строгий UI.
- **tailwind-theme.js** — переключение светлой/тёмной темы.

## 2.1) Первый запуск

Самый короткий путь — создать базу редактора скриптом (нужен PHP 8.2+ с `pdo_sqlite`,
запуск из консоли):

```bash
cd web-tools/editor-studio
php tools/init-db.php --host=127.0.0.1 --database=teeworlds_mrpg \
    --db-user=root --db-password=СЕКРЕТ --demo-guest
```

Скрипт создаёт `data/editor-studio.sqlite` со всей схемой, записывает параметры подключения
к игровой БД, задаёт логин и пароль администратора (пароль печатает один раз; свой можно
задать ключом `--password=...`), а с ключом `--demo-guest` добавляет гостевой аккаунт
`artist / artist123` с тремя открытыми вкладками — чтобы сразу проверить путь
«гость → администратор → БД». Повторный запуск ничего не ломает: переданные аргументы
переопределяют сохранённое, остальное остаётся как было, гостевые аккаунты и запросы
не трогаются. `php tools/init-db.php --describe` показывает, что уже есть в базе,
а `php tools/init-db.php --password=НОВЫЙ` задаёт новый пароль администратора, если
старый забыт.

Если скрипт запустить нечем, те же данные задаются вручную:

1. Скопируйте `data/db-config.example.json` в `data/db-config.json` и заполните доступ
   к игровой БД. При первом запуске эти настройки один раз импортируются в SQLite
   (`data/editor-studio.sqlite`) — дальше их удобнее менять в разделе **Настройки**.
2. **Задайте пароль администратора** в поле `editor_password`. Пароля по умолчанию нет:
   пока поле пустое, вход администратора закрыт, а экран входа так и пишет. Значение может
   быть обычной строкой или хешем `password_hash()` — второй вариант предпочтительнее.
3. Откройте `index.html`, войдите администратором, затем в **Настройки** проверьте
   подключение и при необходимости включите гостевой вход и создайте гостевые аккаунты
   (**Система → Гостевые пользователи**).

Каталог `data/` закрыт `.htaccess` и не попадает в git: конфиг, база SQLite и дампы
остаются на сервере.

Локальный запуск без Apache/Nginx:

```bash
cd web-tools/editor-studio
php -S 127.0.0.1:8080 router.php
```

`router.php` обязателен: встроенный сервер PHP не читает `.htaccess`, и без роутера
`data/editor-studio.sqlite` скачивался бы по прямой ссылке. Роутер отдаёт 404 на
`data/`, `scenarios/*.json`, `.git`, `.env` и файлы `*.sqlite|*.sql|*.db`.

## 3) api/db.php — поддерживаемые справочники (whitelist)

- quests → `tw_quests_list` (ID/Name)
- items → `tw_items_list` (ID/Name)
- worlds → `tw_worlds` (ID/Name)
- skills → `tw_skills_list` (ID/Name)
- bots → `tw_bots_info` (ID/Name)

Конфиг (параметры подключения, лимиты, пароль администратора) хранится в SQLite —
таблица `settings` файла `data/editor-studio.sqlite`. Пароль не возвращается в ответах
API. Файл `data/db-config.json` читается только один раз при первом запуске — для
переноса настроек со старой версии.

Сетевые правила (`allow_remote_editor`, `allowed_editor_ips`) инициализируются один раз
при запуске редактора (`store_init_network_rules()`), а изменяются только напрямую в БД:
`api/db.php` их не отдаёт и не принимает, страница «Настройки» с ними не работает —
так их не может случайно затереть состояние браузера.

## 4) Как добавить новый редактор

1) Создайте страницу: `my-editor.html` (или `.php`).
2) Подключите ядро (минимум):

```html
<script src="editor-core/page-loader.js" data-mode="scenario"></script>
```

3) Добавьте редактор в `studio.manifest.js` (в нужную группу):

```js
{ key: 'my', title: 'Мой редактор', hint: 'Что настраивает вкладка', icon: 'fa-wand-magic', src: 'my-editor.html' },
```

`title` и `hint` — то, что видит пользователь: короткое название и одна строка
пояснения под ним в боковом меню. Внутренние ключи в интерфейсе не показываются.
У каждого редактора одинаковое поведение: кнопка «?» с инструкцией и `Ctrl+S` для сохранения
(`editor-core/help.js`, страницы со своим обработчиком помечают
`<body data-own-save-shortcut="1">`).

Чтобы вкладка могла выдаваться гостям, добавьте её `key` в каталог
`editor_guest_page_catalog()` (`api/db-core.php`) с указанием ресурсов:
`'write'` — что гость может менять через запросы, `'read'` — что только читается.
Без записи в каталоге вкладка гостям недоступна (даже если её включить в UI).

## 5) Синхронизация между БД

Модуль синхронизации позволяет безопасно применять изменения из одной БД в другую.

### Как это работает

1. **Автоматическая запись**: все CRUD-операции (create/update/delete) через `DBCrud` автоматически записываются в историю (localStorage).
2. **Кнопка синхронизации**: появляется в toolbar каждого редактора с badge (количество неприменённых операций).
3. **Проверка схем**: перед применением сравниваются структуры исходной и целевой БД.
4. **Безопасное применение**: операции выполняются в транзакции с полной валидацией.

### Компоненты

- **api/db-sync.php** — серверный API (сравнение схем, применение операций, карта таблиц и обратная загрузка из целевой БД)
- **editor-core/db-sync.js** — клиентский модуль (история, UI, API)
- **Секция в settings.html** — настройка профилей целевых подключений
- **Карта синхронизации в settings.html** — таблица направлений (обе стороны / только загрузка / не синхронизируется)

### Безопасность

- Whitelist таблиц и колонок
- Сравнение схем перед применением
- Транзакции (all-or-nothing)
- Подтверждение фразой «Применить»
- Лимит 1000 операций за раз

### Общие правила безопасности API

- **Роль проверяется до действия.** Гость получает 403 на любую запись
  (`guest_action_guard`), админ — полный доступ.
- **Запись — только JSON-POST с этого же узла** (`guard_write_actions()`):
  проверяются `Content-Type: application/json` и `Origin`. Чтение остаётся
  доступным обычным GET-ом. Так запрос нельзя подделать с постороннего сайта.
- **Подробности ошибок не уходят клиенту.** `editor_safe_message()` пропускает
  только сообщения, написанные для пользователя, остальные заменяет общим
  текстом и пишет в журнал сервера.
- **Проверка внешних адресов** (настройки → «Проверить соединение») не ходит
  в локальную сеть и не следует переадресациям — иначе сервер можно было бы
  использовать как прокси во внутреннюю сеть.

Подробнее см. [SYNC_GUIDE.md](SYNC_GUIDE.md).

### Правила для запросов и диалогов

Любая страница пишет так:

```js
const res = await EditorCore.Http.json('api/db-crud.php?action=list&resource=items');
if (!res.ok) return EditorCore.Page.toast(res.error, 'error');

if (!await EditorCore.Page.confirm('Удалить запись?')) return;      // модальное окно
await EditorCore.Page.withBusy(button, () => save());               // защита от двойного клика
```

Почему так: сеть, таймауты и ошибки — в одном месте; подтверждения выглядят
одинаково и переводятся на английский; кнопка на время запроса блокируется,
поэтому двойной клик не создаёт две записи.

## 5.1) Хранилище: SQLite

Все данные самого редактора (не игровая БД) лежат в `data/editor-studio.sqlite`
(слой — `api/store.php`, PDO SQLite, схема версионируется в `store_schema()`):

| Таблица | Что хранит |
| --- | --- |
| `settings` | настройки подключения к игровой БД, гостевые лимиты, параметры синхронизации |
| `guest_users` | гостевые аккаунты: логин, имя, хеш пароля, включённые вкладки, версия сессии |
| `change_requests` | запросы гостей: автор, статус, снимок операций и анализа |
| `request_messages` | переписка внутри запроса (роль автора, текст, отметки прочтения) |
| `auth_throttle` | счётчики попыток входа (по IP и по паре «IP + логин») |
| `rate_limits` | ограничение частоты действий (отправка запросов, сообщения) |
| `meta` | версия схемы и служебные значения |

Очередь «Синхро» остаётся в браузере (localStorage): это рабочий журнал
администратора, а не общие данные.

Старые JSON-файлы (`db-config.json`, `auth-throttle.json`, `db-sync-config.json`,
`change-requests/*.json`) читаются один раз при первом запуске и импортируются
в SQLite (`store_import_legacy()`); после этого источником истины является база.
Файл базы и его журналы (`*.sqlite-wal`, `*.sqlite-shm`) не попадают в git,
а каталог `data/` закрыт от прямого доступа — см. «Безопасность данных» ниже.

## 6) DB Select одним объявлением

Пример поля, которое хранит **ID**, но показывает **названия из БД**:

```js
quest_id: createField('db_select', 'Квест', 0, { datasource: 'quests' })
```

Для списка ID:

```js
reward_items: createField('db_multiselect', 'Награды', [], { datasource: 'items' })
```

## 7) Гостевые пользователи и запросы на изменение

Гость — это **личный аккаунт**, который создаёт администратор. Гостевых аккаунтов может быть
сколько угодно; у каждого свой логин, пароль и свой набор включённых вкладок редакторов.

Строгая цепочка: **гость → администратор → БД**. Гость не имеет ни одного кодового пути,
который пишет в игровую БД: его правки остаются в браузере и отправляются администратору
как запрос, а применяет запрос только администратор (одной транзакцией).

### Где управлять
**Система → Гостевые пользователи** (`guests-editor.html`, API `api/guests.php`):
- создать аккаунт (имя, логин, пароль);
- для каждого аккаунта включить/выключить **вкладки редакторов** (чекбоксы + «Все»/«Ни одной»);
- выключить аккаунт, сменить пароль, завершить активные сессии, удалить аккаунт;
- видеть, сколько запросов каждого аккаунта ждёт проверки и когда был последний вход.

Общие правила (включение гостевого входа, лимиты, разрешение входа с любых IP) —
в **Система → Запросы гостей → «Правила доступа»**. Лимиты: запросов на рассмотрении,
пауза между отправками, операций в запросе.

### Что видит и делает гость
1. Входит на экране входа во вкладке **«Гость»** (логин + пароль).
2. Видит в меню только те редакторы, которые включил администратор, и страницу **«Мои запросы»**.
3. Правит данные как обычно, но `DBCrud.create/update/remove` не уходят в БД: операции
   складываются в **черновик запроса** в `localStorage` (ключ `editorStudio.guestDraft.v2:<id аккаунта>`).
   Новые записи получают временные ID `2000000000…2000999999`.
4. Списки и формы показывают данные БД **с наложенным черновиком** — гость всегда видит свои
   значения, а не оригинал. Изменённые записи помечаются бейджем «Изменено»/«Новая»,
   в форме — подсказкой «Локальное изменение», в списке — какие поля изменены.
5. На странице «Мои запросы» видит подробный анализ (поле: было → станет, связанные записи,
   каскадные удаления), вводит Nickname и описание (обязательно) и отправляет запрос.

### После отправки
Отправленные операции **не исчезают** из браузера: они помечаются как «В запросе CR-… — на проверке»
и продолжают накладываться на данные. Поэтому, открыв запись повторно, гость видит свой вариант,
а не исходный, и понимает, что он уже в запросе. Изменять такую запись нельзя до решения администратора.

Статус запросов подтягивается автоматически (`Draft.syncSubmitted()`: при открытии страницы,
возврате на вкладку и раз в минуту на странице запросов):
- **принят** — локальные операции снимаются, в БД уже новые значения;
- **отклонён/отозван** — локальные операции снимаются, снова показываются исходные данные;
- **на рассмотрении** — наложение сохраняется.

### Проверки на сервере
- `api/db-crud.php`: гостю доступны только `list/get`, только ресурсы с `guest => true` **и**
  только те, что входят в включённые ему вкладки.
- `api/change-requests.php`: `config/preview/submit/mine/get/withdraw`; операции запроса
  валидируются по включённым вкладкам (`cr_assert_guest_resources`), лимиты и кулдауны — тоже на сервере.
- `api/db.php`: только справочники, конфигурация без секретов.
- `api/guests.php`, `accounts.php`, `db-maintenance.php`, `db-sync.php`, `api.php`: только администратор.
- Выключение аккаунта, смена пароля или «Завершить сессии» сразу инвалидирует существующие
  гостевые сессии (версия сессии в аккаунте). Сессии гостя никогда не содержат прав администратора.
- Запрос принадлежит аккаунту (`author.guestId`), поэтому гость видит свою историю и после
  повторного входа и смены пароля. `guestHash` остаётся только для старых запросов без аккаунта.
- Сессия: cookie `HttpOnly` + `SameSite=Lax` (+`Secure` по HTTPS), строгий режим PHP
  (`session.use_strict_mode`, только cookie), новый id при входе и выходе.
- Подбор пароля ограничен на сервере и **не сбрасывается удалением cookie**:
  таблица `auth_throttle` хранит счётчики по IP (25 попыток / 10 минут → блок 5 минут)
  и по паре «IP + логин» (5 попыток / 10 минут → блок 60 секунд). Успешный вход обнуляет счётчики,
  а чужой адрес не может заблокировать настоящего гостя, подбирая его логин.
- Страницы без выданной вкладки закрыты оверлеем «Вкладка выключена» (UI), сервер отвечает 403.

Запросы, переписка, аккаунты и счётчики попыток входа хранятся в SQLite
(`data/editor-studio.sqlite`, раздел 5.1). Записи идут через транзакции (`store_tx()`),
поэтому сохранение настроек не может потерять аккаунты, а применение запроса
и его пометка «принят» происходят согласованно.

**Миграция со старого режима.** Единый гостевой пароль (`guest_password`) не переносится:
при обновлении личные гостевые аккаунты нужно создать заново, старые гостевые сессии
после обновления недействительны. Если поле осталось в файле `data/db-config.json`,
оно игнорируется, а «Гостевые пользователи» показывают подсказку, что вход общий больше
не работает.

### Переписка гость ↔ администратор
Внутри каждого запроса есть диалог: гость уточняет правку, администратор отвечает
и объясняет решение. Переписка хранится в SQLite (`request_messages`) и привязана
к запросу, поэтому видна обеим сторонам в одном месте.

- **Гость** — в «Мои запросы» → выбранный запрос → блок «Переписка с администратором».
- **Администратор** — в очереди запросов, в карточке запроса → блок «Переписка с гостем».
- **Прочитано / не прочитано.** Сервер хранит `read_by_admin_at` и `read_by_guest_at`
  для каждого сообщения. Открытие диалога помечает входящие сообщения прочитанными;
  непрочитанные показываются с пометкой «новое» и полосой слева, а в списке запросов
  и в меню студии — счётчиком (`unread`). Счётчик гостя складывается с числом
  неотправленных правок в черновике.
- **API** (`api/change-requests.php`): `GET ?action=messages&id=…` — список сообщений
  (помечает входящие прочитанными), `POST ?action=message { id, body }` — отправка.
  Длина сообщения 1–2000 символов, антифлуд 3 секунды, права проверяются на сервере:
  гость пишет только в свои запросы, администратор — в любые.
- **Обновление.** Открытый диалог подтягивает новые сообщения раз в 30 секунд и при
  возврате на вкладку; страница списка запросов обновляет счётчики так же.
- **Удаление запроса** удаляет и переписку (каскад на уровне схемы).

### Локальные изменения и данные БД
Черновик и «отправленные» операции живут только в браузере гостя (`localStorage`, ключ с id аккаунта).
Сервер о них не знает до отправки запроса; после отправки он хранит снимок операций в запросе.
Поэтому:
- гость может потерять черновик, очистив данные браузера — это ожидаемо и безопасно;
- другой браузер/устройство не покажет черновик (но покажет историю запросов);
- при одобрении/отклонении запроса локальные операции снимаются автоматически (`syncSubmitted`).

## 8) Правила интерфейса (одинаковые во всех вкладках)

Редактор рассчитан на человека, который впервые видит базу игры, поэтому все вкладки
ведут себя и выглядят одинаково.

- **Русский и английский интерфейс.** Переключатель RU/EN есть в шапке каждой вкладки
  и на экране входа; выбор запоминается (раздел 9). Названия таблиц (`tw_*`), внутренние
  значения (`all_of`, `sequential`) и ключи вкладок пользователю не показываются —
  вместо них понятные подписи.
- **Одна кнопка «?»** в шапке открывает инструкцию по текущей вкладке
  (`editor-core/help.js`). `Ctrl+S` сохраняет в любом редакторе, `Esc` закрывает окна.
- **Понятные пустые состояния.** Вместо пустого экрана — что произошло и что нажать
  дальше («Данных нет — нажмите «Новый предмет»»).
- **Ошибки видны.** Сервер возвращает `{ error: "…" }` с понятным текстом, тост показывает
  именно его, а не «Ошибка» без подробностей.
- **Текст из БД экранируется.** Списки и заголовки собираются через `escapeHtml()`
  (`editor-core/utils.js`) — название предмета или ника не может вставить разметку.
- **Количество действий минимально.** Список слева, форма справа, три кнопки:
  «Новый …», «Сохранить», «Удалить». Остальное — в подсказке «?».
- **Гость видит своё.** Значения из черновика запроса показываются с пометкой,
  что поле изменено и ждёт проверки администратором (см. раздел 7).

### Дизайн-система (цвет, типографика, ритм)

Оформление задаётся **одним** набором переменных в `editor-core/editor-theme.css`
(первый блок `:root` — тёмная тема, второй — светлая). Страница или компонент не
выбирает цвет сам: он берёт токен, и одинаковые блоки во всех 18 вкладках выглядят
одинаково в обеих темах.

- **Поверхности.** `--editor-bg` (фон страницы) → `--editor-surface` (панель,
  карточка, шапка) → `--editor-surface-2` (вложенный блок, строка списка). Разница
  между ними 2–3% яркости: вложенность читается без дополнительных рамок.
- **Одна линия.** `--editor-line` (волосяная рамка) и `--editor-line-strong`
  (граница наведения/фокуса). Карточки, поля и панели не рисуют тени — тень
  (`--editor-shadow-sm/md/lg`) осталась только у «парящих» слоёв: модалки,
  выпадающие списки, тосты. `.editor-card`, `.editor-section` и `.editor-field`
  специально без `box-shadow`, чтобы форма не превращалась в решётку из рамок.
- **Типографика.** Шкала `--editor-text-xs` 11 / `-sm` 12.5 / `-md` 13.5 / `-lg` 15 /
  `-xl` 22 px. Подпись поля — `.editor-label` (12.5px, 600, приглушённый цвет):
  значение в контроле ярче подписи, поэтому форма читается сверху вниз. Заголовок
  вкладки — 22px/700 с плиткой-иконкой, подзаголовок — `.editor-page-sub`.
- **Ритм.** Отступы только из `--editor-gap-1…6`, радиусы из `--editor-radius-xs…lg`
  (6/8/10/14). Плотность: строка списка `.editor-row` — 1px зазор, сайдбар — 14px
  внутреннего отступа, форма — `--editor-fields-gap` 14px.
- **Семантика вместо палитры.** Страницы не используют `text-slate-*` / `bg-indigo-*`:
  есть `.editor-text`, `.editor-muted-text`, `.editor-hairline`, `.editor-soft`,
  `.editor-primary-*`. `tools/check.mjs` (раздел 4.1) падает, если палитра Tailwind
  вернулась на страницу или из темы пропал ключевой токен.
- **Состояния.** Фокус: `:focus-visible` — 2px контур акцента (виден всегда, в том
  числе при навигации с клавиатуры). Фокус внутри поля подсвечивает подпись.
  Наведение на строку — фон, наведение на карточку — усиление рамки, без подъёма
  и «прыжков». Пустое состояние — `.editor-empty-state`: иконка в плитке и одна
  фраза «что произошло и что нажать».

### Позиция (X/Y) и карта мира

Любая позиция в редакторе — **один элемент**: X и Y в одной строке и кнопка
«Местоположение». Это касается квестов (координаты шага, цель задачи, интерактивная
точка), NPC, мобов и складов — отдельной вёрстки под каждую таблицу больше нет.

- **Вид.** `.editor-vec2`: подпись оси в префиксе, число справа, рядом кнопка
  `.editor-vec2-map` с иконкой и словом «Местоположение». Строка не переносится;
  на ширине ≤720px подпись кнопки скрывается — остаётся иконка, а оси по-прежнему
  стоят рядом (проверяется тестом и `tools/check.mjs`).
- **Как включить.** В схеме поля: `type: 'vec2'`. Если координаты лежат в двух
  колонках БД (`PosX`/`PosY`, `PositionX`/`PositionY`), добавьте
  `ui: { axes: { x: 'PosX', y: 'PosY' }, mapWorldPath: 'WorldID' }`. Для вложенного
  объекта (`Position {x, y}`) достаточно `ui: { mapWorldPath: 'WorldID' }`.
  `ui.mapWorldPath` — путь к миру записи; по нему открывается нужная карта.
- **Окно карты** (`editor-core/point-map.js`). Открывается поверх редактора,
  карту можно двигать мышью, приближать колесом (и кнопками/клавишами `+`/`−`,
  `F` — вся карта, `C` — к точке). Клик по карте ставит точку, маркер можно
  перетаскивать; X/Y правятся и вручную в нижней панели. «Применить» записывает
  обе координаты в поля формы — дальше работает обычная логика формы (черновик
  гостя, «Сохранить», пометка изменённых полей). `Esc` — отмена.
- **Без мира карты нет.** Кнопка не открывает пустое окно: если `WorldID` не выбран,
  редактор подсказывает «сначала выберите мир». Если у мира нет файла карты или
  каталог `maps/` недоступен серверу, окно пишет об этом и предлагает «Повторить».
- **Где лежат файлы.** `api/map.php` берёт карту из `maps/<Path>` (поле `Path`
  таблицы `tw_worlds`), текстуры — из `data/mapres/`. Каталоги ищутся рядом с
  `web-tools/editor-studio` (то есть в корне репозитория) и переопределяются
  переменными окружения `EDITOR_MAPS_DIR` и `EDITOR_MAPRES_DIR` — это нужно,
  если редактор стоит отдельно от игровых данных:

  ```yaml
  # docker-compose: смонтировать карты и текстуры рядом с редактором
  volumes:
    - ../maps:/var/www/maps:ro
    - ../data/mapres:/var/www/mapres:ro
  environment:
    EDITOR_MAPS_DIR: /var/www/maps
    EDITOR_MAPRES_DIR: /var/www/mapres
  ```

### Макет и адаптивность

Все вкладки собираются из одного каркаса — своих сеток и «магических» отступов на
страницах нет. Размеры живут в `editor-core/editor-template.css`, поэтому изменение
одного токена поправляет весь редактор.

- **Каркас страницы.** `.editor-page` (ширина `--editor-page-max`, отступы
  `--editor-page-pad`) → `.editor-page-header` (заголовок, подзаголовок, кнопки) →
  `.editor-page-body`. Полноэкранная вкладка «Сценарии» использует тот же токен с
  модификатором `.editor-page--app` (без отступов и максимальной ширины).
- **Колонки.** `.editor-two-col` — две колонки, на ширине ≤1100px схлопываются в одну;
  `.editor-span-all` растягивает поле на всю строку. Боковая панель — `.editor-shell`
  (`280–320px` + контент), на ≤1100px тоже становится одной колонкой.
- **Списки и таблицы.** `.editor-list-scroll` (модификаторы `--tall`, `--short`,
  `--bare`) вместо инлайновых `style="max-height"`; таблицы — только внутри
  `.editor-table-wrap` (липкая шапка, горизонтальная прокрутка, `min-width` 480→420px).
- **Кнопки.** `.editor-btn--sm` и `.editor-btn--xs` — компактные размеры в шапках и
  строках списков; на сенсорных экранах (`pointer:coarse`) цели увеличиваются до 44px.
- **Текст.** Длинные значения из БД и логины переносятся (`overflow-wrap:anywhere`),
  блоки кода и медиа не выходят за карточку. Тона текста — классы `.editor-tone-danger`,
  `-warning`, `-success`, `-accent` вместо инлайновых `style="color:…"`.
- **Высота экрана.** Везде `100dvh` (с `vh` как запасным вариантом): адресная строка
  мобильного браузера больше не обрезает нижнюю часть окна. Высокие формы прокручиваются
  внутри `.editor-modal-content`.
- **Проверка.** `tools/check.mjs` падает, если на странице нет каркаса `.editor-page`
  и `.editor-page-header`, если вернулись инлайновые пиксельные размеры, `h-screen`
  или таблица без прокручиваемого контейнера.
  Отдельно проверяются шапка/тело/подвал окна компонента, `data-field-path` у булевых
  полей и то, что каждая подпись поля из `registry.js` есть в английском каталоге.
- **Окно компонента (сценарии).** `.editor-modal-shell` — постоянная шапка (иконка
  и название компонента, крестик), прокручиваемое тело `.editor-modal-body` и подвал
  с «Отмена / Сохранить». `Esc` закрывает окно, `Ctrl+S` применяет правки компонента,
  а не сохраняет сценарий; прокрутка сохраняется при добавлении и удалении элементов.
- **Переходы к шагам — всегда отдельной строкой.** Блок `.sc-modal-nav` стоит первым
  во всех компонентах: на каждом шаге подпись слева и список шагов справа
  (`.sc-modal-nav-row`). Туда же попадают ветки `linkTargets` (`branch_random`:
  TRUE/FALSE и подобные) — раньше это были обычные карточки вразнобой с остальными
  полями. На экране уже 560px подпись переносится над полем, строка остаётся одна.
- **Поля компонента — ячейки разной ширины.** `.sc-modal-fields` — flex-контейнер
  с переносом: число и галочка узкие (`.sc-modal-field--narrow`, до 320px), выбор
  и текст средние (до 560px), списки, теги и многострочный текст — на всю строку
  (`--wide`). Медиазапросов нет: строки набираются сами под ширину окна, а одинокое
  поле не растягивается на весь экран благодаря `max-width`.
- **Элементы списков внутри компонента.** У списка четыре режима (`ui.layout`):
  `stack` — поля друг под другом (по умолчанию), `grid` — сетка с шаблоном и `colSpan`
  (крупные формы редакторов БД), `compact` — тонкая шапка «#N … корзина» и поля,
  которые сами укладываются в строки (мобы), `row` — весь элемент в одну строку
  (слот дропа: предмет, количество, шанс; маркер: позиция, здоровье). Ширина ячейки
  берётся из типа поля: число и галочка — узкие, выбор — средний, теги/списки/
  многострочный текст — на всю строку; переопределяется через `ui.cellSize`.
  Кнопка «Добавить элемент» больше не растягивается на всю карточку (`.editor-list-add`).

## 9) Языки интерфейса (RU / EN)

Интерфейс полностью двуязычный: **русский** (исходный, он же по умолчанию) и
**английский**. Переключатель показывается ровно один раз на экран: в студии —
в верхней панели (рядом с кнопкой перезагрузки), на экране входа — в его углу.
Страница редактора, открытая внутри студии, своего переключателя не рисует
(язык общий); если открыть её отдельным файлом — переключатель появляется в её
панели действий. Выбор сохраняется в `localStorage` (`editorStudio.lang`) и
применяется во всех вкладках студии сразу (событие `storage`).

### Как это устроено
- **`editor-core/i18n.js`** — движок: `EditorCore.I18n.t(text, vars)`, `.set(lang)`,
  `.toggle()`, `.locale()`, `.plural(n, one, few, many)`, `.onChange(fn)`.
  Переводит текст узлов, атрибуты (`title`, `placeholder`, `aria-label`, `alt`,
  `data-tooltip`), `<title>`, нативные `alert/confirm/prompt` и — через
  `MutationObserver` — любой узел, который страница добавила после загрузки.
- **`editor-core/i18n-en.js`** — каталог английского языка. Ключ — русская строка
  ровно в том виде, в каком она видна на экране (пробелы нормализованы). Если
  перевода нет, показывается русская строка: интерфейс остаётся рабочим, а не
  «пустым» местом или техническим ключом.
- **Подстановки.** Ключ может содержать `{0}`, `{1}` — такие записи превращаются
  в шаблоны и совпадают с уже отрисованным текстом («Показано: 12» → «Showing: 12»).
  Значение использует те же `{0}`, `{1}` по порядку подстановок в ключе; подставленные
  значения тоже переводятся, если совпадают со строкой каталога (текст ошибки внутри
  сообщения).
- **Числительные.** `I18n.plural(n, 'операция', 'операции', 'операций')` возвращает
  русскую форму по правилам RU или английскую единственную/множественную.
- **Даты и числа.** `I18n.locale()` → `ru-RU` / `en-US`; используется в форматировании дат.
- **Нативные диалоги** (`alert`, `confirm`, `prompt`) переводятся на входе, поэтому
  в английском режиме не остаётся русских окон.
- **Сообщения сервера** (`{ ok: false, error: "…" }`) приходят по-русски и переводятся
  на клиенте по каталогу — сервер не зависит от языка интерфейса.

### Как добавить перевод
1. Найдите русскую строку в интерфейсе (она же ключ).
2. Добавьте пару в каталог `editor-core/i18n-en.js`: `"Русская строка": "English string"`.
3. Если строка собирается в коде из значений — пишите ключ с `{0}`, `{1}`
   и вызывайте `EditorCore.I18n.t('Шаблон {0}', [value])` там, где значение неизвестно заранее.
4. Ничего не помечать в разметке не нужно. Если фрагмент переводить нельзя
   (например, пример JSON или имя таблицы) — поставьте на контейнер `data-i18n-skip`.

## 10) Безопасность данных

Всё, что относится к самому редактору, лежит в `data/`:

| Файл | Что внутри |
| --- | --- |
| `editor-studio.sqlite` | пароль администратора (хеш), доступ к игровой БД, гостевые аккаунты, запросы и переписка |
| `db-config.json` | только для первичного импорта (старые установки); содержит пароль игровой БД |
| `db-dumps/` | дампы игровой базы |
| `change-requests/` | старый формат запросов гостей (после миграции) |

Ни один из этих файлов не должен отдаваться веб-сервером. По умолчанию это уже
так: в каталоге лежит `data/.htaccess` с `Require all denied`, а Docker-конфиг
(`apache-config.conf`) закрывает `/data` на уровне vhost. Дополнительно `.sqlite`
и `db-config.json` исключены из git — конфиг с паролем в репозиторий не попадает
(в репозитории остаётся только `db-config.example.json`).

Защита включена по умолчанию в четырёх местах, чтобы не зависеть от конфигурации
конкретного хостинга:

| Окружение | Чем закрыто |
| --- | --- |
| Apache (хостинг, AllowOverride All) | `data/.htaccess`, `scenarios/.htaccess` |
| Docker (образ из этого каталога) | `apache-config.conf`: `<Directory data>` и `<Directory scenarios>` |
| Встроенный сервер `php -S` | `router.php` (см. «Первый запуск») |
| git | `.gitignore`: `data/*.sqlite*`, `data/*.json` (кроме `db-config.example.json`) |

**Nginx / FrankenPHP / Caddy `.htaccess` не читают** — если редактор стоит за ними,
запрет нужно добавить в конфиг сайта:

```nginx
# nginx: внутрь /data не пускаем никого, PHP работает через /api
location ^~ /data/ { deny all; return 404; }
# на всякий случай: файлы состояния не должны отдаваться и по прямому пути
location ~* \.(sqlite|sqlite-wal|sqlite-shm)$ { deny all; return 404; }
```

```caddy
# Caddyfile
@data path /data/*
respond @data 404
```

Проверка после установки (должен быть `403`/`404`, но не `200`):

```bash
curl -sI http://ВАШ-СЕРВЕР/data/editor-studio.sqlite | head -1
curl -sI http://ВАШ-СЕРВЕР/data/db-config.json | head -1
```

Если хочется убрать базу из веб-корня совсем, путь можно переопределить
переменной окружения `EDITOR_STUDIO_SQLITE` (например,
`/var/lib/editor-studio/editor-studio.sqlite`) — тогда `data/` остаётся только
для дампов и импорта. Права на файл базы выставляются `0640` при создании.

Что уже сделано на стороне приложения:

- пароль администратора хранится только хешем (`password_hash`), открытым текстом
  принимается лишь в старых конфигах;
- подбор пароля ограничен: `auth_throttle` (по IP и по паре «IP + логин»);
- все изменяющие запросы — только JSON-POST с этого же узла
  (`require_same_origin_json_post`), гость не может писать в игровую БД;
- SQL-ошибки драйвера не отдаются клиенту (только в журнал сервера);
- имена файлов сценариев санитизируются (`api.php`), размер ограничен;
- `api/map.php` отдаёт файлы только из `maps/` и `data/mapres/`: путь и имя
  проверяются (`..`, абсолютные пути и подмена расширения отклоняются), итоговый
  файл обязан остаться внутри каталога-источника, ответ кешируется по ETag;
- карта доступна администратору и гостю, у которого открыта хотя бы одна вкладка
  с координатами; данные читаются только из БД и файлов, записи нет.

### Сборка CSS

Tailwind поставляется локально в `editor-core/tailwind.css` (файл хранится в Git).
Node.js на сервере не требуется. После изменения классов в HTML/JS выполните
из каталога `web-tools/editor-studio`: `npm ci && npm run build:css`.
Конфигурация темы и forms-плагина: `tailwind.config.cjs`.
Проверки: `npm test`.
