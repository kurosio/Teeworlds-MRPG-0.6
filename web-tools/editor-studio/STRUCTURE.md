# Editor Studio — структура и ядро

Этот пакет содержит **единое ядро UI + DB** и несколько редакторов, подключаемых как независимые страницы.

## 1) Корень проекта

- **index.html** — *Editor Studio*: оболочка (адаптивная) переключает iframe на нужный редактор.
  Оформление оболочки (сайдбар, пункт меню `.studio-item`, шапка рабочей области, экран
  входа) собрано на тех же токенах, что и вкладки, поэтому переход между меню и
  редактором не выглядит переходом в другое приложение.

  Меню по умолчанию — **рельс**: виден только столбец иконок (~64px), рабочая область
  получает максимум места. Наведение курсора или фокус с клавиатуры раскрывает панель
  поверх рабочей области (`.studio-sidebar.is-open`), когда область неактивна — она
  снова сжимается до иконок. Панель вынесена из потока (`.studio-sidebar__panel`
  абсолютная), поэтому iframe редактора при раскрытии не пересобирается. Кнопка в
  шапке или в подвале меню (Ctrl+B, `body.studio-sidebar-pinned`) закрепляет панель
  открытой — тогда она занимает место в раскладке. На тач-устройствах (нет hover)
  панель по умолчанию закреплена, а до 768px используется выдвижное меню
  (`.studio-drawer`). В раскрытой панели живут фильтр по названию/подсказке/ключевым
  словам и секции «Избранное» (звезда у пункта) и «Недавние» — отдельно для каждой
  роли, в localStorage. Группы меню сворачиваются кликом по заголовку (состояние
  тоже по роли; при фильтрации временно раскрываются, в рельсе игнорируются), а
  ширину закреплённой панели можно тянуть за правый край, 220–440px (двойной
  клик сбрасывает). Клавиша `/` ставит фокус в фильтр. Быстрый переход — палитра
  команд **Ctrl+K** (`editor-core/studio-palette.js`): редакторы и действия
  оболочки одним списком, открытые вкладки — в начале списка.

  Открытые редакторы — **keep-alive вкладки**: список открытых вкладок
  сохраняется по роли (`studio.tabs.*`) и переживает перезагрузку страницы, а
  iframe создаётся лениво при первом выборе вкладки. Каждый живой редактор —
  свой кадр (`#studioFrames`), переключение только прячет/показывает кадры и
  не теряет несохранённые формы. Одновременно держатся до 5 кадров; вытесняется
  давно не использовавшийся и только без несохранённой работы (dirty-check тем
  же протоколом, что и при перезагрузке) — сама вкладка при этом не закрывается.
  Полоса вкладок над рабочей областью (`#studioTabs`, Ctrl+Tab — цикл,
  Alt+1…9 — по номеру) закрывает редактор с подтверждением при несохранённых
  правках; вкладки переставляются перетаскиванием, закрываются средней кнопкой
  мыши, а закрытую возвращает Ctrl+Shift+T. Отдельно от порядка вкладок ведётся
  **история переходов** между редакторами: Alt+←/→ и кнопки «назад/вперёд» в
  шапке возвращают к предыдущему редактору, как в браузере. Клавиши оболочки
  работают и когда фокус внутри редактора: кадр пересылает их студии сообщением
  `editor-shell:navigate` (пересылка — в `ui-manager.js`, приём — только от
  известных кадров в `index.html`). Внешний вид (режим темы, акцент, плотность) настраивается
  в окне «Appearance» и применяется ко всем кадрам через `EditorCore.prefs`;
  клавиша `?` показывает справку по горячим клавишам. Стили оболочки вынесены
  в `editor-core/studio-shell.css`.
- **studio.manifest.js** — список редакторов Studio, сгруппированных по категориям (файлы / БД / система). Поле `keywords` у пункта подкармливает фильтр меню и палитру Ctrl+K.
- **scenario-editor.html** — редактор сценариев.
- **settings.html** — вкладка настроек (подключение к БД + просмотр источников списков + настройка синхронизации).
- **database.html** — вкладка управления БД (подключение, дампы, восстановление).
- **vouchers-editor.html** — редактор ваучеров (CRUD напрямую в БД, использует ядро).
- **bots-info-editor.html** — редактор ботов (tw_bots_info).
- **bots-npc-editor.html** — редактор NPC (tw_bots_npc).
- **worlds-editor.html** — редактор миров (tw_worlds).
- **aethers-editor.html** — редактор телепортов Aethers (tw_aethers).
- **change-requests.html** — запросы на изменение: для гостя — черновик + отправка (идемпотентно, с видимым обратным отсчётом кулдауна) + экспорт/импорт черновика файлом + «Мои запросы»; для администратора — очередь с постраничной подгрузкой, фильтр по разделу, массовое отклонение/удаление, шаблоны комментариев, вкладка журнала аудита, общие лимиты гостевого доступа.
- **guests-editor.html** — гостевые пользователи (только администратор): создание аккаунтов, пароли (политика сервера + генератор), включение/выключение, набор доступных вкладок, индивидуальные лимиты и срок действия каждого гостя.
- **api.php** — файловый API для сценариев (список/загрузка/сохранение JSON в `scenarios/`). Только администратор.
- **api/db.php** — безопасный DB API (конфиг + справочники для DB Select).
- **api/db-core.php** — общие helper-функции для DB API (конфиг + подключение) и вся сессионная безопасность: жизненный цикл сессии (idle/absolute timeout, SameSite=Strict, path только на студию), CSRF-токены, доверенные прокси и определение IP клиента, политика паролей, эффективные лимиты гостя, запись аудита (`editor_audit`).
- **api/db-maintenance.php** — API для дампов/восстановления БД.
- **api/db-crud.php** — универсальный CRUD API для DB-редакторов (ресурсы описываются в карте на сервере).
- **api/db-sync.php** — API для синхронизации между БД (сравнение схем, применение операций).
- **api/auth.php** — вход администратора/гостя (личный логин + пароль гостевого аккаунта), статус сессии, выдача CSRF-токена (`action=csrf`), выход. Проверка пароля timing-safe: dummy-verify выполняется всегда.
- **api/guests.php** — управление гостевыми аккаунтами (только администратор): list/create/update/password/revoke/delete.
- **api/db-resources.php** — общая карта ресурсов (таблицы, колонки, ссылки, обратные FK, доступность для гостя).
- **api/change-requests.php** + **api/change-requests-lib.php** — API запросов гостей (проверка, анализ влияния, конфликты, применение одной транзакцией, переписка гость ↔ администратор).
- **api/map.php** — карта мира и её текстуры для окна «Местоположение»: отдаёт
  `maps/<tw_worlds.Path>` и `data/mapres/*.png` (только чтение, только своим).
- **vendor/ddnet-map/** — локальный рендер карт DDNet (`twwebgl.js`, `twdatafile.js`,
  `picker.html/css/js`). Карта рисуется в браузере без интернета; лицензии и
  список изменений — в `vendor/ddnet-map/NOTICE.md`.
- **vendor/fontawesome/**, **vendor/sortable/** — локальные иконки
  Font Awesome 6 (только solid + regular) и SortableJS. Студия
  не ходит на CDN: работает офлайн.
  Веб-шрифтов нет: интерфейс использует системный шрифтовой стек платформы.
- **editor-core/position-picker.js + position-picker.css** — единый UI-элемент
  позиции для всех редакторов (`type: 'vec2'` и кастомных полей задач квестов).
  Карточка показывает закреплённую точку, мир, координаты и активные флаги карты;
  кнопки открывают `PointMap` или ручной ввод X/Y. Мир задаётся
  `ui.mapWorldPath` (сохранение в существующее поле формы) либо программно через
  `PositionPicker.setWorldId()` / `onWorldChange()` / `openMap({ worldId })`.
  Флаги `ui.safeTiles`, `showTiles`, `highlightTiles`, `radiusPath`, `grid`, `snap`
  управляют слоями и валидацией в окне карты. Новых колонок БД элемент не требует.
- **editor-core/map-worlds.js** — общий кэш списка миров, парсинг ID (мир 0
  валиден) и «последний выбранный мир» для карточки позиции и окна карты.
- **editor-core/point-map.js** — только диалог карты (iframe, список миров при
  отсутствии мира записи, запись X/Y, события `editor-map:*`). Политику мира и
  флаги получает от `PositionPicker`; БД и localStorage напрямую не читает.
- **api/store.php** — хранилище Editor Studio на SQLite: настройки, гостевые аккаунты, счётчики попыток входа, лимиты частоты, запросы на изменение и переписка, журнал аудита и ключи идемпотентной отправки (схема v4). Все данные редактора живут в одном файле `data/editor-studio.sqlite`.

### Быстрая проверка перед отправкой

```bash
node web-tools/editor-studio/tools/check.mjs
```

Полный прогон перед коммитом (из папки студии): `npm test` (node:test) и
`node tests/php-harness.mjs` (синтаксис PHP и чистые функции безопасности/лимитов;
нужен опциональный `php-wasm`: `npm install --no-save php-wasm`).

Скрипт без зависимостей проверяет синтаксис всех страниц и модулей, следит, чтобы
не вернулись убранные приёмы (прямой `fetch`, нативный `confirm`, захардкоженная
локаль дат), проверяет файлы `localization/` и падает, если строка интерфейса
осталась без перевода: источник интерфейса английский, словари — в `localization/`.

`tools/dialog-preview.html` — витрина диалогового модуля без базы данных: панель
форматов, всплывающий список записей и чипы подстановок. Достаточно открыть файл
через любой статический сервер (`python3 -m http.server` в этой папке) — удобно
для ручной проверки после правок `editor-core/dialog-editor.js`.

## 2) editor-core/ — единый набор UI-компонентов и утилит

### Инициализация
- **bootstrap.js** — единая точка входа для редакторов: подключает тему, toasts, запускает UI Manager.
- **ui-manager.js** — *Core UI Manager*: 
  - автозагрузка `DB Select` (`EditorCore.DB.init()`),
  - validation hints (`data-validate`),
  - синхронизация Toggle (`data-checked`),
  - навигация по записям во всех редакторах: над списком — кнопки
    «предыдущая/следующая» и позиция «N / M», по списку ходят стрелками
    (и Home/End/PgUp/PgDn), Tab заходит в список один раз (roving tabindex),
    активная строка подкручивается в видимую область, фокус переживает
    перерисовку списка. Работает по DOM (`.editor-row`, узлы дерева квестов,
    `.cr-list-item`), поэтому покрывает и DbEditor, и редакторы со своей
    логикой списка; выбор строки всегда делает сам редактор (клик по строке)
    со всеми его проверками несохранённых правок. Список с собственной
    контекстной навигацией помечается `data-record-nav-off` (дерево квестов):
    общая планка не ставится, клавиатура и возврат фокуса остаются.

### Компоненты и рендеринг полей
- **field-renderer.js** — рендерит поля по JSON-схеме:
  - Input (text/number/password)
  - Textarea
  - Select / Multiselect
  - Date / Time / Datetime
  - Checkbox / Toggle
  - Modal (через `ui.js`)
  - DB Select / DB Multiselect (`type: db_select`, `db_multiselect`)

### Схемы и конфигурация
- **registry.js** — библиотека схем (JSON-конфиги полей/компонентов/действий). Здесь заменены ID-поля на DB Select (quests/items/worlds/bots).
- **defaults.js** — дефолтные стили/параметры для форм и модалок.

### UI и утилиты
- **ui.js** — модальные окна, toasts, базовые UI-хелперы + Tabs (не завязаны на конкретный редактор).
- **utils.js** — общие функции: экранирование, `qs`, `debounce`, безопасные path helpers,
  ограниченный TTL/LRU request-cache, `setStatus`, `Dirty`, загрузка файлов и JSON-запросы.
  Здесь же чистая логика навигации bespoke-редакторов: каталог крафтов «путь + плоский
  список» (`craftNavSegments/InPath/Children/PathFields/PrunePath` — хлебные крошки и чипсы
  вместо селектов-фильтров и сворачиваемого дерева) и стабильное дерево квестов
  (`matchQuestTree` — порядок по ID, поиск по квесту или его шагам). Оба редактора
  запоминают место работы в `localStorage` (`mrpgEditor:craftsNav:v1` / `questsNav:v1`)
  и сами открывают прямые ссылки `?record=`.
- **http.js** — единственный сетевой слой: `EditorCore.Http.json(url, options)` и
  `Http.request()` (то же, но бросает исключение), `Http.text()`. Внутри — таймаут
  (15 с по умолчанию), отмена через `AbortSignal`, разбор ответа с «мусором» перед
  JSON, единый результат `{ ok, status, error, data }` и сообщение оболочке на 401.
  Здесь же same-origin `postMessage` helpers с проверкой источника и без wildcard.
  Страницы и модули не вызывают `fetch` напрямую — так у всех запросов одинаковые
  таймаут, обработка ошибок и реакция на истёкшую сессию. Здесь же живёт CSRF:
  токен сессии кэшируется в `sessionStorage`, подставляется в каждый POST
  заголовком `X-Editor-CSRF`, при `403 csrf_token` обновляется и запрос
  повторяется один раз; ответы 429 отдают поле `retryAfter`.
- **page-kit.js** — то, что нужно каждой странице: `EditorCore.Page` с `esc`, `t`
  (перевод), `locale`, `fmtDate`, `plural`, `toast`, `debounce`, `api`, `withBusy`,
  `confirm`/`alert` (общий модальный диалог вместо нативного `confirm()` с
  переводом кнопок), `report` (журнал неожиданных ошибок).
- **core.js** — базовая инициализация EditorCore.

### DB слой
- **db.js** — клиент к `api/db.php` + кеширование + автозаполнение `<select data-datasource="...">`.
- **db-crud.js** — клиент к `api/db-crud.php` (list/get/create/update/delete, `rawRow()` — строка без черновика гостя) для DB-редакторов. Автоматически записывает операции для синхронизации; в request-preview разрешает только чтение, а в admin `edit=1` направляет mutations в `RequestContext`/`revise`, минуя прямую запись в игровую БД.
- **db-sync.js** — модуль синхронизации между БД: история изменений, проверка схем, применение операций, UI.
- **guest-mode.js** — гостевой режим (`EditorCore.Guest`): роль и аккаунт, черновик запроса в localStorage (по каждому гостевому аккаунту отдельно), наложение черновика и отправленных запросов на данные БД, синхронизация версий ревизий, блокировка недоступных вкладок, плашка гостя. Черновик экспортируется/импортируется одним JSON-файлом (`Draft.exportDraft`/`importDraft`, только неотправленные операции; временные ID при коллизиях перевыпускаются), а `Draft.submitKey()` даёт стабильный ключ идемпотентности для текущего состава черновика — повторная отправка не создаёт дубликат.
- **change-markers.js** — общие маркеры изменённых записей и полей для generic и кастомных редакторов, включая дерево квестов и вложенные поля.
- **request-context.js** — request-aware контекст редактора: read-only preview по обычной ссылке, а для администратора с `edit=1` — привычные формы с наложенным snapshot, versioned mutations и batch-сохранение операций через `revise`.
- **request-workbench.js** — модальное редактирование pending-запроса гостем и общие editor URL/deep-link helpers
  (`editorUrl()`, `recordLinkAttrs()`); администратор использует обычный редактор через `RequestContext`, а не popup.
- **deep-link.js** — переход по ссылке «открыть запись» (`?record=…&field=…`): нажимает строку `data-id`
  в списке и подсвечивает поле; при `?request=…` не вмешивается (см. раздел 7).
- **i18n.js** — движок перевода: `EditorCore.I18n` (`t`, `set`, `toggle`, `locale`, `plural`, `onChange`). Источник строк — английский текст разметки и кода; язык `en` ничего не переводит, остальные берут словарь из `localization/`. Переводит разметку, атрибуты (`title`, `placeholder`, `aria-label`), динамически добавленные узлы (наблюдатель за DOM) и нативные `alert/confirm`; выбор языка хранится в `localStorage` (`editorStudio.lang`, по умолчанию `en`).
- **`localization/index.js`** — реестр языков: `sourceLanguage`, `defaultLanguage`, манифест `files` и `register()`. Любой файл `lang_<код>.js` из папки подключается манифестом и появляется в переключателе (см. раздел 9).

### Упрощение создания редакторов
- **page-loader.js** — подключает тему, иконки, Tailwind и файлы ядра одним тегом
  (`<script src="editor-core/page-loader.js">`). Иконки локальные
  (`vendor/fontawesome/`), шрифты системные; если локальные стили не загрузились, один раз предупреждает об этом,
  вместо того чтобы оставить страницу без оформления.
- **form-runtime.js** — минимальный schema-runtime: 2-way binding, list add/remove, переиспользуемый в новых редакторах.
- **dialog-editor.js** — реплики диалога (NPC-редактор и шаг квеста): тексты, режим линии, левый/правый
  спикер. Порядок реплик меняется перетаскиванием за рукоятку, кнопками ↑/↓ и клавиатурой (рукоятка
  в фокусе, `ArrowUp`/`ArrowDown`); перестановка реализована внутри модуля, поэтому не зависит от
  Sortable с CDN и работает на странице, где внешняя библиотека не подключена.

  **Форматы реплики.** Над полем текста — панель «Bot / Item / World» и игровые подстановки
  `<player>`, `<time>`, `<here>`, `<eidolon>`. Выбор записи открывает всплывающий список с поиском
  (он вынесен в `body` и не обрезается панелями); список берётся из справочников страницы
  (`formats: { bot, world }` — `Map` или массив), а если их нет — из БД (`bots`, `items`, `worlds`)
  лениво и с кэшем. Число в поиске всегда можно применить как готовый ID. Под полем чипы показывают,
  что уже вставлено: имя записи и `#ID`; клик по чипу меняет запись, крестик убирает подстановку,
  неизвестный ID подсвечивается. Справа в панели — длина реплики в байтах и лимит игры (1024).
  Подстановки те же, что заменяет сервер в
  `src/game/server/core/components/Bots/DialogsData.cpp`.
- **db-editor-runtime.js** — компактный runtime для CRUD-редакторов БД (список + форма + сохранение).
  Запоминает последнюю открытую запись (`editor-core:last-record:<ресурс>`) и
  открывает редактор на ней после перезагрузки; перерисовка списка сохраняет
  его прокрутку.
- **help.js** — кнопка «?» в шапке каждого редактора: короткая инструкция по вкладке
  (порядок работы, смысл полей, правила для гостя) и общий `Ctrl+S`.

### Тема
- **editor-theme.css** — единые CSS variables + строгий UI: нейтральная тёмная тема (zinc + indigo) и светлая, акцентные пресеты (`data-editor-accent`: indigo/teal/violet/amber), компактная плотность (`data-editor-density=compact`), глобальный видимый `:focus-visible` и поддержка `prefers-reduced-motion`. Шрифт UI — системный стек платформы (`--editor-font`): веб-шрифты не загружаются, текст рендерится нативным шрифтом ОС. Имена переменных и классов стабильны.
- **tailwind-theme.js** — предпочтения внешнего вида (`EditorCore.prefs`): режим темы (тёмная/светлая/системная), акцент и плотность. Хранятся в localStorage (`editor-theme-mode`, `editor-accent`, `editor-density`), выставляются атрибутами на `<html>`/`<body>` и разносятся по оболочке и всем iframe; `EditorCore.theme` остался совместимым фасадом поверх resolved-темы.
- **studio-shell.css** — стили оболочки `index.html`: рельс меню, keep-alive вкладки, палитра команд, экран входа.
- **studio-palette.js** — палитра команд Ctrl+K: чистые функции ранжирования (`filter`/`scoreItem`/`scoreText`/`prioritize`, покрыты тестами без DOM) + клавиатурный DOM-оверлей.

## 2.1) Первый запуск

Самый короткий путь — создать базу редактора скриптом (нужен PHP 8.2+ с `pdo_sqlite`,
запуск из консоли):

```bash
cd web-tools/editor-studio
php tools/init-db.php --host=127.0.0.1 --database=teeworlds_mrpg \
    --db-user=root --db-password=СЕКРЕТ --demo-guest
```

Скрипт создаёт `data/editor-studio.sqlite` со всей схемой, записывает параметры подключения
к игровой БД, задаёт логин и пароль администратора (пароль печатает один раз; свой можно
задать ключом `--password=...`), а с ключом `--demo-guest` добавляет гостевой аккаунт
`artist / artist123` с тремя открытыми вкладками — чтобы сразу проверить путь
«гость → администратор → БД». Повторный запуск ничего не ломает: переданные аргументы
переопределяют сохранённое, остальное остаётся как было, гостевые аккаунты и запросы
не трогаются. `php tools/init-db.php --describe` показывает, что уже есть в базе,
а `php tools/init-db.php --password=НОВЫЙ` задаёт новый пароль администратора, если
старый забыт.

Если скрипт запустить нечем, те же данные задаются вручную:

1. Скопируйте `data/db-config.example.json` в `data/db-config.json` и заполните доступ
   к игровой БД. При первом запуске эти настройки один раз импортируются в SQLite
   (`data/editor-studio.sqlite`) — дальше их удобнее менять в разделе **Настройки**.
2. **Задайте пароль администратора** в поле `editor_password`. Пароля по умолчанию нет:
   пока поле пустое, вход администратора закрыт, а экран входа так и пишет. Значение может
   быть обычной строкой или хешем `password_hash()` — второй вариант предпочтительнее.
3. Откройте `index.html`, войдите администратором, затем в **Настройки** проверьте
   подключение и при необходимости включите гостевой вход и создайте гостевые аккаунты
   (**Система → Гостевые пользователи**).

Каталог `data/` закрыт `.htaccess` и не попадает в git: конфиг, база SQLite и дампы
остаются на сервере.

Локальный запуск без Apache/Nginx:

```bash
cd web-tools/editor-studio
php -S 127.0.0.1:8080 router.php
```

`router.php` обязателен: встроенный сервер PHP не читает `.htaccess`, и без роутера
`data/editor-studio.sqlite` скачивался бы по прямой ссылке. Роутер отдаёт 404 на
`data/`, `scenarios/*.json`, `.git`, `.env` и файлы `*.sqlite|*.sql|*.db`.

## 3) api/db.php — поддерживаемые справочники (whitelist)

- quests → `tw_quests_list` (ID/Name)
- items → `tw_items_list` (ID/Name)
- worlds → `tw_worlds` (ID/Name)
- skills → `tw_skills_list` (ID/Name)
- bots → `tw_bots_info` (ID/Name)

Конфиг (параметры подключения, лимиты, пароль администратора) хранится в SQLite —
таблица `settings` файла `data/editor-studio.sqlite`. Пароль БД не возвращается в ответах
API: `get_config` отдаёт только булевый признак `password_set`, а `save_config` меняет
пароль лишь при непустом `password` или явном `clear_password`. Поэтому открытие страницы
«Настройки» само по себе ничего не меняет в пароле, а пустое поле формы означает
«оставить сохранённый пароль». Файл `data/db-config.json` читается только один раз при
первом запуске — для переноса настроек со старой версии.

Сетевые правила (`allow_remote_editor`, `allowed_editor_ips`) инициализируются один раз
при запуске редактора (`store_init_network_rules()`), а изменяются только напрямую в БД:
`api/db.php` их не отдаёт и не принимает, страница «Настройки» с ними не работает —
так их не может случайно затереть состояние браузера.

## 4) Как добавить новый редактор

1) Создайте страницу: `my-editor.html` (или `.php`).
2) Подключите ядро (минимум):

```html
<script src="editor-core/page-loader.js" data-mode="scenario"></script>
```

3) Добавьте редактор в `studio.manifest.js` (в нужную группу):

```js
{ key: 'my', title: 'Мой редактор', hint: 'Что настраивает вкладка', icon: 'fa-wand-magic', src: 'my-editor.html' },
```

`title` и `hint` — то, что видит пользователь: короткое название и одна строка
пояснения под ним в боковом меню. Внутренние ключи в интерфейсе не показываются.
У каждого редактора одинаковое поведение: кнопка «?» с инструкцией и `Ctrl+S` для сохранения
(`editor-core/help.js`, страницы со своим обработчиком помечают
`<body data-own-save-shortcut="1">`).

Чтобы вкладка могла выдаваться гостям, добавьте её `key` в каталог
`editor_guest_page_catalog()` (`api/db-core.php`) с указанием ресурсов:
`'write'` — что гость может менять через запросы, `'read'` — что только читается.
Без записи в каталоге вкладка гостям недоступна (даже если её включить в UI).

### Когда изменение считается изменением

Формы редактирования не умеют отличать SQL `NULL` от пустого ввода: `rowToModel()`
приводит `NULL` к `''` или `0`, а сохранение отправляет тот же набор полей обратно.
Поэтому «нет значения» — это одно состояние, выраженное по-разному, и сравнивать
значения нужно одной функцией, а не `===`:

- **`EditorCore/utils.js`** — `utils.valuesEqual(a, b)` (плюс `isEmptyValue()` и
  `canonicalValue()`). `null`, `undefined`, `false`, `0`, `''`, `'0'`, `'0.00'`, `[]`,
  `{}`, `'[]'`, `'{}'` равны между собой; числа и JSON сравниваются по смыслу
  (`7` = `'7.00'`, `'{"a":1}'` = `'{"a": 1}'`). Этой функцией пользуются
  `guest-mode.js` (черновик гостя) и `request-context.js` (правка запроса админом).
- **`api/db-resources.php`** — те же правила на сервере: `editor_values_equal()`,
  `editor_value_canonical()`, `editor_value_is_empty()`, `editor_decode_json_value()`.
  Обёртки `cr_values_equal()` / `cr_canonical()` в `change-requests-lib.php` вызывают
  их, своих копий правил нет.
- **Пустое поле не пишется.** `db-crud.php` (`action=update`) и `db-sync.php`
  (`apply_operations`) сначала читают текущую строку и записывают только реально
  отличающиеся колонки, а при полном совпадении возвращают `{ok: true, unchanged: true}`
  и не трогают ни строку, ни историю синхронизации. `cr_apply()` делает то же перед
  применением: запрос, созданный до этого правила, не заменит `NULL` на `''`/`0`.
- **Пустой запрос не создаётся.** `cr_analyze()` помечает операцию с совпадающими
  значениями как `noop`, diff-карточка показывает «нет изменённых полей», а
  `cr_prepare_for_submit()` отбрасывает такие операции и на полностью пустом наборе
  отвечает «Изменения совпадают с текущими данными — запрашивать нечего».

## 5) Синхронизация между БД

Модуль синхронизации позволяет безопасно применять изменения из одной БД в другую.

### Как это работает

1. **Автоматическая запись**: все CRUD-операции (create/update/delete) через `DBCrud` автоматически записываются в историю (localStorage).
2. **Кнопка синхронизации**: появляется в toolbar каждого редактора с badge (количество неприменённых операций).
3. **Проверка схем**: перед применением сравниваются структуры исходной и целевой БД.
4. **Безопасное применение**: операции выполняются в транзакции с полной валидацией.

### Компоненты

- **api/db-sync.php** — серверный API (сравнение схем, применение операций, карта таблиц и обратная загрузка из целевой БД)
- **editor-core/db-sync.js** — клиентский модуль (история, UI, API)
- **Секция в settings.html** — настройка профилей целевых подключений
- **Карта синхронизации в settings.html** — таблица направлений (обе стороны / только загрузка / не синхронизируется)

### Безопасность

- Whitelist таблиц и колонок
- Сравнение схем перед применением
- Транзакции (all-or-nothing)
- Подтверждение фразой «Применить»
- Лимит 1000 операций за раз

### Общие правила безопасности API

- **Роль проверяется до действия.** Гость получает 403 на любую запись
  (`guest_action_guard`), админ — полный доступ.
- **Запись — только JSON-POST с этого же узла** (`guard_write_actions()`):
  проверяются `Content-Type: application/json` и `Origin`. Чтение остаётся
  доступным обычным GET-ом. Так запрос нельзя подделать с постороннего сайта.
- **CSRF-токен в каждом POST.** Сервер требует заголовок `X-Editor-CSRF`
  с токеном сессии (synchronizer token): токен выдаётся `api/auth.php?action=csrf`
  и в ответах status/login/logout, ротируется при входе и выходе; Origin-проверка —
  только дополнительный слой.
- **Сессии ограничены по времени**: idle 12 часов, absolute 7 дней (настройки
  `session_idle_seconds`/`session_absolute_seconds` с клампами), кука
  `SameSite=Strict` и path только на каталог студии, ID сессии ротируется
  при входе/выходе/истечении.
- **Всё важное пишется в аудит**: входы, изменения гостевых аккаунтов, отправка,
  ревизии, решения администратора (включая массовые) — таблица `audit_log`,
  у администратора есть вкладка «Журнал аудита».
- **IP клиента не берётся из заголовков вслепую**: `X-Forwarded-For`/`X-Real-IP`
  учитываются, только если `REMOTE_ADDR` входит в доверенные прокси
  (настройка `trusted_proxies` или env `EDITOR_STUDIO_TRUSTED_PROXIES`, по умолчанию пусто).
- **Подробности ошибок не уходят клиенту.** `editor_safe_message()` пропускает
  только сообщения, написанные для пользователя, остальные заменяет общим
  текстом и пишет в журнал сервера.
- **Проверка внешних адресов** (настройки → «Проверить соединение») не ходит
  в локальную сеть и не следует переадресациям — иначе сервер можно было бы
  использовать как прокси во внутреннюю сеть.

Подробнее см. [SYNC_GUIDE.md](SYNC_GUIDE.md). Модель угроз, принятые меры и
чек-лист развёртывания — в [SECURITY.md](SECURITY.md).

### Правила для запросов и диалогов

Любая страница пишет так:

```js
const res = await EditorCore.Http.json('api/db-crud.php?action=list&resource=items');
if (!res.ok) return EditorCore.Page.toast(res.error, 'error');

if (!await EditorCore.Page.confirm('Удалить запись?')) return;      // модальное окно
await EditorCore.Page.withBusy(button, () => save());               // защита от двойного клика
```

Почему так: сеть, таймауты и ошибки — в одном месте; подтверждения выглядят
одинаково и переводятся на английский; кнопка на время запроса блокируется,
поэтому двойной клик не создаёт две записи.

## 5.1) Хранилище: SQLite

Все данные самого редактора (не игровая БД) лежат в `data/editor-studio.sqlite`
(слой — `api/store.php`, PDO SQLite, схема версионируется в `store_schema()`):

| Таблица | Что хранит |
| --- | --- |
| `settings` | настройки подключения к игровой БД, гостевые лимиты, параметры синхронизации |
| `guest_users` | гостевые аккаунты: логин, имя, хеш пароля, включённые вкладки, версия сессии, индивидуальные лимиты (JSON), срок действия |
| `change_requests` | запросы гостей: автор, статус, снимок операций и анализа |
| `request_messages` | переписка внутри запроса (роль автора, текст, отметки прочтения) |
| `auth_throttle` | счётчики попыток входа (по IP и по паре «IP + логин») |
| `rate_limits` | ограничение частоты действий (отправка запросов, сообщения) |
| `audit_log` | журнал аудита: актор (роль/ID/имя), действие, запрос, детали, IP (хранится последние 5000) |
| `submit_keys` | ключи идемпотентности отправки запросов: повтор с тем же ключом возвращает уже созданный запрос |
| `meta` | версия схемы и служебные значения |

Очередь «Синхро» остаётся в браузере (localStorage): это рабочий журнал
администратора, а не общие данные.

Старые JSON-файлы (`db-config.json`, `auth-throttle.json`, `db-sync-config.json`,
`change-requests/*.json`) читаются один раз при первом запуске и импортируются
в SQLite (`store_import_legacy()`); после этого источником истины является база.
Файл базы и его журналы (`*.sqlite-wal`, `*.sqlite-shm`) не попадают в git,
а каталог `data/` закрыт от прямого доступа — см. «Безопасность данных» ниже.

## 7) Гостевые пользователи и запросы на изменение

Гость — это **личный аккаунт**, который создаёт администратор. Гостевых аккаунтов может быть
сколько угодно; у каждого свой логин, пароль и свой набор включённых вкладок редакторов.

Строгая цепочка: **гость → администратор → БД**. Гость не имеет ни одного кодового пути,
который пишет в игровую БД: его правки остаются в браузере и отправляются администратору
как запрос, а применяет запрос только администратор (одной транзакцией).

### Где управлять
**Система → Гостевые пользователи** (`guests-editor.html`, API `api/guests.php`):
- создать аккаунт (имя, логин, пароль);
- для каждого аккаунта включить/выключить **вкладки редакторов** (чекбоксы + «Все»/«Ни одной»);
- выключить аккаунт, сменить пароль, завершить активные сессии, удалить аккаунт;
- видеть, сколько запросов каждого аккаунта ждёт проверки и когда был последний вход.

Изменения в списке видны сразу, без перезагрузки страницы: карточка обновляется по ответу
сервера, а удалённая исчезает немедленно (оптимистично) и затем сверяется с БД. Поздний ответ
устаревшего запроса список не возвращает. Удаление аккаунта завершает его сессии: следующий
запрос гостя получает отказ, и оболочка возвращает его на экран входа. Вкладки, выданные
аккаунту, перечитываются у открытых сессий по событию `editor-shell:guest-account-changed`.

Общие правила (включение гостевого входа, лимиты, разрешение входа с любых IP) —
в **Система → Запросы гостей → «Правила доступа»**. Лимиты: запросов на рассмотрении,
пауза между отправками, операций в запросе.

### Что видит и делает гость
1. Входит на экране входа во вкладке **«Гость»** (логин + пароль).
2. Видит в меню только те редакторы, которые включил администратор, и страницу **«Мои запросы»**.
3. Правит данные как обычно, но `DBCrud.create/update/remove` не уходят в БД: операции
   складываются в **черновик запроса** в `localStorage` (ключ `editorStudio.guestDraft.v2:<id аккаунта>`).
   Новые записи получают временные ID `2000000000…2000999999`.
4. Списки и формы показывают данные БД **с наложенным черновиком** — гость всегда видит свои
   значения, а не оригинал. Изменённые записи помечаются бейджем «Изменено»/«Новая»,
   в форме — подсказкой «Локальное изменение», в списке — какие поля изменены. Во время ввода
   поле и запись получают отдельную transient-пометку ещё до сохранения в черновик.
5. На странице «Мои запросы» видит подробный анализ (поле: было → станет, связанные записи,
   каскадные удаления), вводит Nickname и описание (обязательно) и отправляет запрос.

### После отправки
Отправленные операции **не исчезают** из браузера: они помечаются как «В запросе CR-… — на проверке»
и продолжают накладываться на данные. Поэтому, открыв запись повторно, гость видит свой вариант,
а не исходный, и понимает, что он уже в запросе. Прямое повторное изменение той же записи в редакторе
блокируется, но весь pending-запрос можно открыть кнопкой **«Править запрос»** и дополнить или
исправить через workbench — в том числе после просьбы администратора в переписке.

Каждая ревизия увеличивает `version`; сохранение и принятие проверяют её на сервере. Если другая
сторона уже сохранила новую версию, старое окно не перезаписывает её: нужно сначала посмотреть свежий
diff. Администратор нажимает **«Править в редакторе»** и исправляет тот же состав операций в привычной
форме редактора: обычные «Сохранить/Создать/Удалить» вызывают `revise`, а не прямую запись в БД.
Составные изменения квеста и групповое переименование крафтов объединяются в одну ревизию. После
возврата к запросу администратор принимает уже исправленную версию. Из admin diff ссылки ведут к записи
и конкретному полю в этом editable request-режиме; остальные deep links остаются read-only preview.

Черновик общий для всех документов студии: его пишет и оболочка, и редактор внутри iframe, и
соседняя вкладка. Поэтому `readDraft()` доверяет своему снимку только пока сохранённое значение
совпадает с тем, из которого он был разобран, — иначе счётчики («Мои запросы» в меню, вкладки
«Черновик»/«Мои запросы» на странице запросов) показывали бы уже удалённые правки. Бейдж в меню
пересчитывается по сообщению `editor-shell:guest-draft-changed`, по событию `storage` (другая
вкладка), при возврате на вкладку и раз в минуту; одновременные подсчёты не перезаписывают
друг друга (ответ применяется только от последнего запроса).

Статус запросов подтягивается автоматически (`Draft.syncSubmitted()`: при открытии страницы,
возврате на вкладку и раз в минуту на странице запросов):
- **принят** — локальные операции снимаются, в БД уже новые значения;
- **отклонён/отозван** — локальные операции снимаются, снова показываются исходные данные;
- **на рассмотрении** — наложение сохраняется; если администратор сохранил новую ревизию,
  локальные операции обновляются по номеру версии (без автоматического rebase открытого старого окна).

### Проверки на сервере
- `api/db-crud.php`: гостю доступны только `list/get`, только ресурсы с `guest => true` **и**
  только те, что входят в включённые ему вкладки.
- `api/change-requests.php`: `config/preview/submit/mine/get/revise/withdraw` (у администратора также
  `list/approve/reject/message`); `revise` повторно нормализует операции, анализирует их по текущей БД
  и проверяет владельца/роль и `version`. Операции гостя валидируются по включённым вкладкам
  (`cr_assert_guest_resources`), лимиты и кулдауны — тоже на сервере. `approve` применяет сохранённые
  операции последней проверенной версии одной транзакцией.
- `api/db.php`: только справочники, конфигурация без секретов.
- `api/guests.php`, `accounts.php`, `db-maintenance.php`, `db-sync.php`, `api.php`: только администратор.
- Выключение аккаунта, смена пароля или «Завершить сессии» сразу инвалидирует существующие
  гостевые сессии (версия сессии в аккаунте). Сессии гостя никогда не содержат прав администратора.
- Запрос принадлежит аккаунту (`author.guestId`), поэтому гость видит свою историю и после
  повторного входа и смены пароля. `guestHash` остаётся только для старых запросов без аккаунта.
- Сессия: cookie `HttpOnly` + `SameSite=Lax` (+`Secure` по HTTPS), строгий режим PHP
  (`session.use_strict_mode`, только cookie), новый id при входе и выходе.
- Подбор пароля ограничен на сервере и **не сбрасывается удалением cookie**:
  таблица `auth_throttle` хранит счётчики по IP (25 попыток / 10 минут → блок 5 минут)
  и по паре «IP + логин» (5 попыток / 10 минут → блок 60 секунд). Успешный вход обнуляет счётчики,
  а чужой адрес не может заблокировать настоящего гостя, подбирая его логин.
- Страницы без выданной вкладки закрыты оверлеем «Вкладка выключена» (UI), сервер отвечает 403.

Запросы, переписка, аккаунты и счётчики попыток входа хранятся в SQLite
(`data/editor-studio.sqlite`, раздел 5.1). Записи идут через транзакции (`store_tx()`),
поэтому сохранение настроек не может потерять аккаунты, а применение запроса
и его пометка «принят» происходят согласованно.

**Миграция со старого режима.** Единый гостевой пароль (`guest_password`) не переносится:
при обновлении личные гостевые аккаунты нужно создать заново, старые гостевые сессии
после обновления недействительны. Если поле осталось в файле `data/db-config.json`,
оно игнорируется, а «Гостевые пользователи» показывают подсказку, что вход общий больше
не работает.

### Переписка гость ↔ администратор
Внутри каждого запроса есть диалог: гость уточняет правку, администратор отвечает
и объясняет решение. Переписка хранится в SQLite (`request_messages`) и привязана
к запросу, поэтому видна обеим сторонам в одном месте.

- **Гость** — в «Мои запросы» → выбранный запрос → блок «Переписка с администратором».
- **Администратор** — в очереди запросов, в карточке запроса → блок «Переписка с гостем».
- **Прочитано / не прочитано.** Сервер хранит `read_by_admin_at` и `read_by_guest_at`
  для каждого сообщения. Открытие диалога помечает входящие сообщения прочитанными;
  непрочитанные показываются с пометкой «новое» и полосой слева, а в списке запросов
  и в меню студии — счётчиком (`unread`). Счётчик гостя складывается с числом
  неотправленных правок в черновике.
- **API** (`api/change-requests.php`): `GET ?action=messages&id=…` — список сообщений
  (помечает входящие прочитанными), `POST ?action=message { id, body }` — отправка.
  Длина сообщения 1–2000 символов, антифлуд 3 секунды, права проверяются на сервере:
  гость пишет только в свои запросы, администратор — в любые.
- **Обновление.** Открытый диалог подтягивает новые сообщения раз в 30 секунд и при
  возврате на вкладку; страница списка запросов обновляет счётчики так же.
- **Удаление запроса** удаляет и переписку (каскад на уровне схемы).

### Локальные изменения и данные БД
Черновик и «отправленные» операции живут только в браузере гостя (`localStorage`, ключ с id аккаунта).
Сервер о них не знает до отправки запроса; после отправки он хранит снимок операций в запросе.
Поэтому:
- гость может потерять черновик, очистив данные браузера — это ожидаемо и безопасно;
- другой браузер/устройство не покажет черновик (но покажет историю запросов);
- при одобрении/отклонении запроса локальные операции снимаются автоматически (`syncSubmitted`).

### Ссылки из запроса в редакторы
Каждая операция и каждое изменённое поле в diff имеет ссылку на запись. Адрес собирает
`RequestWorkbench.recordLinkAttrs()` — один код и для страницы «Запросы», и для окна правки
запроса (`editor-core/request-workbench.js`). Два режима:

- **`mode: 'request'`** (администратор) — `items-editor.html?request=…&resource=items&record=…&field=…`;
  для pending-запроса добавляется `edit=1` — это разрешение на request-revision mode, а не на
  прямую запись в БД;
- **`mode: 'guest'`** (гость) — `items-editor.html?resource=items&record=…&field=…`: обычный
  редактор, где поверх строки БД показан черновик гостя. Так гость из «Моих запросов» или из
  черновика сразу открывает нужную запись и продолжает работу. Записи, помеченные на удаление,
  ссылки не получают — в черновике её уже нет.

Внутри `index.html` ссылка передаётся через same-origin `postMessage` в shell (`editorSource()`
пропускает только `request/resource/record/field/edit`), в отдельной вкладке работает как обычный
URL. Для `quest_bots` используется общий `quests-editor.html`; временный ID созданной записи после
принятия разрешается через `review.idMap` в реальный ID.

Переход по `?record=…&field=…` выполняет `editor-core/deep-link.js`: он ждёт, пока список отрисует
строку `data-id`, нажимает её (тот же путь, что у пользователя, — поэтому работают и простые
CRUD-редакторы, и дерево квестов) и подсвечивает поле (`.field-link-target`). Если строки нет в
загруженной части списка, `DbEditor` дочитывает запись по ID через `DBCrud.get`. При наличии
`?request=…` модуль отключается: выбором записи и подсветкой поля управляет `request-context.js`.

### Отмена одного поля («изм.» → кнопка)
Поле, которое гость изменил и сохранил в черновик, помечено меткой «изм.». Рядом с меткой —
маленькая кнопка отмены (`guest-field-revert`, `editor-core/editor-template.css`): она убирает
это поле из операции черновика и возвращает значение из базы.

- Клик обрабатывает `DbEditor` (`editor-core/db-editor-runtime.js`): `DBCrud.rawRow()` читает
  строку **без** черновика, `Guest.Draft.revertField()` убирает колонку из операции (и удаляет
  операцию целиком, если изменённых полей не осталось), затем в форму подставляется значение
  `rowToModel()` — остальные несохранённые правки формы не теряются.
- Если прочитать строку не удалось, черновик не меняется: форма и черновик не расходятся.
- Кнопки нет у новых записей (у них нет исходного значения в БД) и у отправленных операций —
  такую правку можно изменить только через «Править запрос» или отзыв запроса.
- Кнопка есть только в гостевом черновике: `RequestContext` (снимок запроса) и админский режим
  правки запроса работают по своим правилам.
- Кнопка реализована в общем CRUD-редакторе (`DbEditor`: предметы, миры, подземелья, аэтэры).
  В кастомных редакторах (крафты, склады, квесты, NPC…) метка «изм.» остаётся, но кнопки нет:
  там отмена делается через «Правка запроса». Чтобы добавить её в кастомный редактор, достаточно
  вызвать `Guest.Draft.revertField()` и перечитать запись — данные и метки обновятся сами.

Preview получает операции с сервера, повторно показывает их поверх списка/формы и помечает все записи
и поля запроса. Без `edit=1` он предназначен только для проверки: `DBCrud` отклоняет create/update/
delete/rename. В admin edit-режиме те же привычные контролы доступны, но mutations собирают операции
запроса, проверяют optimistic `version` и сохраняют их через `revise`; после `version_conflict`
старый редактор блокируется до повторного открытия актуального запроса.

## 8) Правила интерфейса (одинаковые во всех вкладках)

Редактор рассчитан на человека, который впервые видит базу игры, поэтому все вкладки
ведут себя и выглядят одинаково.

- **Русский и английский интерфейс.** Переключатель RU/EN есть в шапке каждой вкладки
  и на экране входа; выбор запоминается (раздел 9). Названия таблиц (`tw_*`), внутренние
  значения (`all_of`, `sequential`) и ключи вкладок пользователю не показываются —
  вместо них понятные подписи.
- **Одна кнопка «?»** в шапке открывает инструкцию по текущей вкладке
  (`editor-core/help.js`). `Ctrl+S` сохраняет в любом редакторе, `Esc` закрывает окна.
- **Понятные пустые состояния.** Вместо пустого экрана — что произошло и что нажать
  дальше («Данных нет — нажмите «Новый предмет»»).
- **Ошибки видны.** Сервер возвращает `{ error: "…" }` с понятным текстом, тост показывает
  именно его, а не «Ошибка» без подробностей.
- **Текст из БД экранируется.** Списки и заголовки собираются через `escapeHtml()`
  (`editor-core/utils.js`) — название предмета или ника не может вставить разметку.
- **Количество действий минимально.** Список слева, форма справа, три кнопки:
  «Новый …», «Сохранить», «Удалить». Остальное — в подсказке «?».
- **Гость видит своё.** Значения из черновика запроса показываются с пометкой,
  что поле изменено и ждёт проверки администратором (см. раздел 7).

### Дизайн-система (цвет, типографика, ритм)

Оформление задаётся **одним** набором переменных в `editor-core/editor-theme.css`
(первый блок `:root` — тёмная тема, второй — светлая). Страница или компонент не
выбирает цвет сам: он берёт токен, и одинаковые блоки во всех 18 вкладках выглядят
одинаково в обеих темах.

- **Поверхности.** `--editor-bg` (фон страницы) → `--editor-surface` (панель,
  карточка, шапка) → `--editor-surface-2` (вложенный блок, строка списка). Разница
  между ними 2–3% яркости: вложенность читается без дополнительных рамок.
- **Одна линия.** `--editor-line` (волосяная рамка) и `--editor-line-strong`
  (граница наведения/фокуса). Карточки, поля и панели не рисуют тени — тень
  (`--editor-shadow-sm/md/lg`) осталась только у «парящих» слоёв: модалки,
  выпадающие списки, тосты. `.editor-card`, `.editor-section` и `.editor-field`
  специально без `box-shadow`, чтобы форма не превращалась в решётку из рамок.
- **Типографика.** Шкала `--editor-text-xs` 11 / `-sm` 12.5 / `-md` 13.5 / `-lg` 15 /
  `-xl` 22 px. Подпись поля — `.editor-label` (12.5px, 600, приглушённый цвет):
  значение в контроле ярче подписи, поэтому форма читается сверху вниз. Заголовок
  вкладки — 22px/700 с плиткой-иконкой, подзаголовок — `.editor-page-sub`.
- **Ритм.** Отступы только из `--editor-gap-1…6`, радиусы из `--editor-radius-xs…lg`
  (6/8/10/14). Плотность: строка списка `.editor-row` — 1px зазор, сайдбар — 14px
  внутреннего отступа, форма — `--editor-fields-gap` 14px.
- **Семантика вместо палитры.** Страницы не используют `text-slate-*` / `bg-indigo-*`:
  есть `.editor-text`, `.editor-muted-text`, `.editor-hairline`, `.editor-soft`,
  `.editor-primary-*`. `tools/check.mjs` (раздел 4.1) падает, если палитра Tailwind
  вернулась на страницу или из темы пропал ключевой токен.
- **Состояния.** Фокус: `:focus-visible` — 2px контур акцента (виден всегда, в том
  числе при навигации с клавиатуры). Фокус внутри поля подсвечивает подпись.
  Наведение на строку — фон, наведение на карточку — усиление рамки, без подъёма
  и «прыжков». Пустое состояние — `.editor-empty-state`: иконка в плитке и одна
  фраза «что произошло и что нажать».

### Позиция (X/Y) и карта мира

Любая позиция в редакторе — **один UI-элемент** `EditorCore.PositionPicker`:
карточка закреплённой точки, подложка «Мир», «Изменить позицию» (карта) и
рядом «Ввести вручную». Это касается квестов (координаты шага, цель задачи,
интерактивная точка), NPC, мобов, дверей подземелий, аэтров, складов и
компонентов сценариев — отдельной вёрстки под каждую таблицу больше нет.

- **Как включить.** В схеме поля: `type: 'vec2'`. Для двух колонок БД —
  `ui: { axes: { x: 'PosX', y: 'PosY' }, mapWorldPath: 'WorldID' }`, для
  вложенного `Position {x, y}` достаточно `ui: { mapWorldPath: 'WorldID' }`.
  Скрытые X/Y (`data-position-axis`) остаются обычными полями формы: FormRuntime,
  валидация, гостевые правки и сохранение не меняются. Новых колонок БД нет.
- **Флаги карты** задаются там же, в `ui`, и подсвечивают нужные динамические
  слои прямо в окне: `safeTiles: true` (нельзя COLLIDE/DEATH/UNHOOK),
  `showTiles`, `highlightTiles`, `radiusPath`, `grid`, `snap`. Активные флаги видны
  метками на карточке. Мобы, NPC, шаги и цели заданий используют `safeTiles`:
  точка на запрещённом тайле остаётся на месте, лишь блокируется «Применить».
  Панель «Инструменты размещения» изначально свёрнута. Игровой слой и сетка
  включаются при открытии только явными `showTiles: true` и `grid: true`;
  без них они выключены и не восстанавливаются из других оверлеев или прошлого
  посещения. Полный список — в `editor-core/EDITOR_GUIDE.md`.
- **Три модуля вместо дублей.** `editor-core/position-picker.js` — сам элемент и
  единственная точка открытия карты; `editor-core/point-map.js` — только диалог с
  iframe; `editor-core/map-worlds.js` — общий кэш списка миров, парсинг ID
  (мир 0 валиден) и «последний выбранный мир». Раньше карточка и окно карты
  независимо грузили миры и парсили ID — теперь одна точка правды.
- **Окно карты.** Двигается мышью, приближается колесом (`+`/`−`, `F` — вся
  карта, `C` — к точке). Клик ставит точку, маркер крупный, с подписью X/Y;
  перетаскивание и ручной ввод в нижней панели тоже работают. «Применить»
  записывает обе координаты в скрытые поля формы, `Esc` — отмена. Выбранный в
  окне мир фиксируется только вместе с точкой: при отмене предпросмотр мира
  сбрасывается.
- **Без мира карты нет.** Если мир не выбран, окно предлагает выбрать его
  встроенным списком. Если у мира нет файла карты или каталог `maps/` недоступен
  серверу, окно пишет об этом и предлагает «Повторить».
- **Где лежат файлы.** `api/map.php` берёт карту из `maps/<Path>` (поле `Path`
  таблицы `tw_worlds`), текстуры — из `data/mapres/`. Каталоги ищутся рядом с
  `web-tools/editor-studio` (то есть в корне репозитория) и переопределяются
  переменными окружения `EDITOR_MAPS_DIR` и `EDITOR_MAPRES_DIR` — это нужно,
  если редактор стоит отдельно от игровых данных:

  ```yaml
  # docker-compose: смонтировать карты и текстуры рядом с редактором
  volumes:
    - ../maps:/var/www/maps:ro
    - ../data/mapres:/var/www/mapres:ro
  environment:
    EDITOR_MAPS_DIR: /var/www/maps
    EDITOR_MAPRES_DIR: /var/www/mapres
  ```

### Макет и адаптивность

Все вкладки собираются из одного каркаса — своих сеток и «магических» отступов на
страницах нет. Размеры живут в `editor-core/editor-template.css`, поэтому изменение
одного токена поправляет весь редактор.

- **Каркас страницы.** `.editor-page` (ширина `--editor-page-max`, отступы
  `--editor-page-pad`) → `.editor-page-header` (заголовок, подзаголовок, кнопки) →
  `.editor-page-body`. Полноэкранная вкладка «Сценарии» использует тот же токен с
  модификатором `.editor-page--app` (без отступов и максимальной ширины).
- **Колонки.** `.editor-two-col` — две колонки, на ширине ≤1100px схлопываются в одну;
  `.editor-span-all` растягивает поле на всю строку. Боковая панель — `.editor-shell`
  (`280–320px` + контент), на ≤1100px тоже становится одной колонкой.
- **Списки и таблицы.** `.editor-list-scroll` (модификаторы `--tall`, `--short`,
  `--bare`) вместо инлайновых `style="max-height"`; таблицы — только внутри
  `.editor-table-wrap` (липкая шапка, горизонтальная прокрутка, `min-width` 480→420px).
- **Кнопки.** `.editor-btn--sm` и `.editor-btn--xs` — компактные размеры в шапках и
  строках списков; на сенсорных экранах (`pointer:coarse`) цели увеличиваются до 44px.
- **Текст.** Длинные значения из БД и логины переносятся (`overflow-wrap:anywhere`),
  блоки кода и медиа не выходят за карточку. Тона текста — классы `.editor-tone-danger`,
  `-warning`, `-success`, `-accent` вместо инлайновых `style="color:…"`.
- **Высота экрана.** Везде `100dvh` (с `vh` как запасным вариантом): адресная строка
  мобильного браузера больше не обрезает нижнюю часть окна. Высокие формы прокручиваются
  внутри `.editor-modal-content`.
- **Проверка.** `tools/check.mjs` падает, если на странице нет каркаса `.editor-page`
  и `.editor-page-header`, если вернулись инлайновые пиксельные размеры, `h-screen`
  или таблица без прокручиваемого контейнера.
  Отдельно проверяются шапка/тело/подвал окна компонента, `data-field-path` у булевых
  полей и то, что каждая подпись поля из `registry.js` есть в английском каталоге.
- **Окно компонента (сценарии).** `.editor-modal-shell` — постоянная шапка (иконка
  и название компонента, крестик), прокручиваемое тело `.editor-modal-body` и подвал
  с «Отмена / Сохранить». `Esc` закрывает окно, `Ctrl+S` применяет правки компонента,
  а не сохраняет сценарий; прокрутка сохраняется при добавлении и удалении элементов.
- **Переходы к шагам — всегда отдельной строкой.** Блок `.sc-modal-nav` стоит первым
  во всех компонентах: на каждом шаге подпись слева и список шагов справа
  (`.sc-modal-nav-row`). Туда же попадают ветки `linkTargets` (`branch_random`:
  TRUE/FALSE и подобные) — раньше это были обычные карточки вразнобой с остальными
  полями. На экране уже 560px подпись переносится над полем, строка остаётся одна.
- **Поля компонента — ячейки разной ширины.** `.sc-modal-fields` — flex-контейнер
  с переносом: число и галочка узкие (`.sc-modal-field--narrow`, до 320px), выбор
  и текст средние (до 560px), списки, теги и многострочный текст — на всю строку
  (`--wide`). Медиазапросов нет: строки набираются сами под ширину окна, а одинокое
  поле не растягивается на весь экран благодаря `max-width`.
- **Элементы списков внутри компонента.** У списка четыре режима (`ui.layout`):
  `stack` — поля друг под другом (по умолчанию), `grid` — сетка с шаблоном и `colSpan`
  (крупные формы редакторов БД), `compact` — тонкая шапка «#N … корзина» и поля,
  которые сами укладываются в строки (мобы), `row` — весь элемент в одну строку
  (слот дропа: предмет, количество, шанс; маркер: позиция, здоровье). Ширина ячейки
  берётся из типа поля: число и галочка — узкие, выбор — средний, теги/списки/
  многострочный текст — на всю строку; переопределяется через `ui.cellSize`.
  Кнопка «Добавить элемент» больше не растягивается на всю карточку (`.editor-list-add`).

## 9) Языки интерфейса (EN — источник, RU — перевод)

Интерфейс написан по-английски: это язык исходников и язык по умолчанию для нового
пользователя. Русский — отдельный словарь в папке `localization/`, который
подключается на лету; тот же механизм работает для любого другого языка.
Переключатель показывается ровно один раз на экран: в студии — в верхней панели
(рядом с кнопкой перезагрузки), на экране входа — в его углу. Страница редактора,
открытая внутри студии, своего переключателя не рисует (язык общий); если открыть
её отдельным файлом — переключатель появляется в её панели действий. Выбор
сохраняется в `localStorage` (`editorStudio.lang`) и применяется во всех вкладках
студии сразу (событие `storage`).

### Из чего состоит система

```
localization/
  index.js     реестр: sourceLanguage='en', defaultLanguage='en', манифест files
  lang_en.js   'en': пустой словарь (язык источника ничего не переводит)
  lang_ru.js   'ru': ~2200 пар «английский текст → русский перевод» + plurals
```

- **`localization/index.js`** — реестр языков. Каждый файл языка вызывает
  `window.EditorCoreLocalization.register({ code, name, short, locale, strings, plurals, pluralIndex })`.
  Манифест `files` перечисляет, какие файлы подключать: браузер не умеет читать
  список файлов папки (тем более при открытии с диска), поэтому новый язык
  добавляется двумя шагами — файл + строка в манифесте.
- **`editor-core/i18n.js`** — движок: `EditorCore.I18n.t(text, vars)`, `.set(lang)`,
  `.toggle()`, `.locale()`, `.plural(n, one, many)`, `.onChange(fn)`.
  Переводит текст узлов, атрибуты (`title`, `placeholder`, `aria-label`, `alt`,
  `data-tooltip`), `<title>`, нативные `alert/confirm/prompt` и — через
  `MutationObserver` — любой узел, который страница добавила после загрузки.
- **`editor-core/page-loader.js`** — разворачивает манифест в теги
  `<script src="localization/lang_xx.js">` (в синхронной ветке — через
  `document.write` при разборе, в асинхронной — по одному скрипту), так что
  страницам не нужно перечислять языки у себя.
- **`localization/lang_ru.js`** — русский перевод. Ключ — ровно тот английский
  текст, который виден на экране (пробелы нормализованы). Если перевода нет,
  показывается исходная английская строка: интерфейс остаётся рабочим.

### Как добавить язык

1. Создайте `localization/lang_de.js` с вызовом
   `window.EditorCoreLocalization.register({ code: 'de', name: 'Deutsch', short: 'DE', locale: 'de-DE', strings: { 'Save': 'Speichern' } })`.
2. Добавьте `'lang_de.js'` в массив `files` в `localization/index.js`.
3. Всё: язык появится в переключателе, а его выбор сохранится в `localStorage`.
   Не хватающие пары берутся из английского источника, так что переводить можно
   постепенно.

### Как добавить перевод строки

1. Найдите английский текст в интерфейсе (он же ключ).
2. Добавьте пару в `localization/lang_ru.js`: `"Save changes": "Сохранить изменения"`.
3. Если строка собирается в коде из значений — пишите ключ с `{0}`, `{1}`
   и вызывайте `EditorCore.I18n.t('Found: {0}', [count])`.
4. Ничего не помечать в разметке не нужно. Если фрагмент переводить нельзя
   (пример JSON, имя таблицы) — поставьте на контейнер `data-i18n-skip`.

### Правила, на которых всё держится

- **Подстановки.** Ключ может содержать `{0}`, `{1}` — такие записи превращаются
  в шаблоны и совпадают с уже отрисованным текстом («Found: 12» → «Найдено: 12»).
  Значение использует те же `{0}`, `{1}` по порядку подстановок в ключе;
  подставленные значения тоже переводятся, поэтому имя профиля «Connection 2»
  внутри русской фразы становится «Подключение 2».
- **Выбор шаблона.** Если подходят несколько ключей, берётся тот, который оставляет
  подстановкам меньше всего текста: иначе общий «{0} · {1}» перехватил бы
  «ID 5 · World: Лес» и половина строки осталась бы английской.
- **Составные подписи.** Строку, склеенную из готовых кусков («World #3 · buy»),
  движок переводит по частям — отдельного ключа на каждую комбинацию не нужно.
- **Значения из базы не переводятся.** Перечисления `Type`/`Group` предметов,
  флаги квестов, эффекты мобов и группы склада уходят обратно в базу, поэтому
  остаются английскими в обоих режимах. Они перечислены в `DATA_STRINGS`
  (`tools/check.mjs`), `DATA_TERMS` (`tools/i18n-audit.mjs`) и в тесте
  `tests/i18n-ui-strings.test.cjs`.
- **Числительные.** `I18n.plural(n, 'line', 'lines')` возвращает форму по правилам
  языка: у русского — три формы из `plurals` под ключом английского единственного
  числа (`строка` / `строки` / `строк`), у английского — one/other.
- **Даты и числа.** `I18n.locale()` → `en-US` / `ru-RU`; используется в форматировании дат.
- **Нативные диалоги** (`alert`, `confirm`, `prompt`) переводятся на входе, поэтому
  в русском режиме не остаётся английских окон, а в английском — русских.
- **Сообщения сервера** (`{ ok: false, error: "…" }`) приходят по-английски (язык
  источника) и переводятся на клиенте по каталогу — сервер не зависит от языка
  интерфейса.

## 10) Безопасность данных

Всё, что относится к самому редактору, лежит в `data/`:

| Файл | Что внутри |
| --- | --- |
| `editor-studio.sqlite` | пароль администратора (хеш), доступ к игровой БД, гостевые аккаунты, запросы и переписка |
| `db-config.json` | только для первичного импорта (старые установки); содержит пароль игровой БД |
| `db-dumps/` | дампы игровой базы |
| `change-requests/` | старый формат запросов гостей (после миграции) |

Ни один из этих файлов не должен отдаваться веб-сервером. По умолчанию это уже
так: в каталоге лежит `data/.htaccess` с `Require all denied`, а Docker-конфиг
(`apache-config.conf`) закрывает `/data` на уровне vhost. Дополнительно `.sqlite`
и `db-config.json` исключены из git — конфиг с паролем в репозиторий не попадает
(в репозитории остаётся только `db-config.example.json`).

Защита включена по умолчанию в четырёх местах, чтобы не зависеть от конфигурации
конкретного хостинга:

| Окружение | Чем закрыто |
| --- | --- |
| Apache (хостинг, AllowOverride All) | `data/.htaccess`, `scenarios/.htaccess` |
| Docker (образ из этого каталога) | `apache-config.conf`: `<Directory data>` и `<Directory scenarios>` |
| Встроенный сервер `php -S` | `router.php` (см. «Первый запуск») |
| git | `.gitignore`: `data/*.sqlite*`, `data/*.json` (кроме `db-config.example.json`) |

**Nginx / FrankenPHP / Caddy `.htaccess` не читают** — если редактор стоит за ними,
запрет нужно добавить в конфиг сайта:

```nginx
# nginx: внутрь /data не пускаем никого, PHP работает через /api
location ^~ /data/ { deny all; return 404; }
# на всякий случай: файлы состояния не должны отдаваться и по прямому пути
location ~* \.(sqlite|sqlite-wal|sqlite-shm)$ { deny all; return 404; }
```

```caddy
# Caddyfile
@data path /data/*
respond @data 404
```

Проверка после установки (должен быть `403`/`404`, но не `200`):

```bash
curl -sI http://ВАШ-СЕРВЕР/data/editor-studio.sqlite | head -1
curl -sI http://ВАШ-СЕРВЕР/data/db-config.json | head -1
```

Если хочется убрать базу из веб-корня совсем, путь можно переопределить
переменной окружения `EDITOR_STUDIO_SQLITE` (например,
`/var/lib/editor-studio/editor-studio.sqlite`) — тогда `data/` остаётся только
для дампов и импорта. Права на файл базы выставляются `0640` при создании.

Что уже сделано на стороне приложения:

- пароль администратора хранится только хешем (`password_hash`), открытым текстом
  принимается лишь в старых конфигах;
- подбор пароля ограничен: `auth_throttle` (по IP и по паре «IP + логин»);
- все изменяющие запросы — только JSON-POST с этого же узла
  (`require_same_origin_json_post`), гость не может писать в игровую БД;
- SQL-ошибки драйвера не отдаются клиенту (только в журнал сервера);
- имена файлов сценариев санитизируются (`api.php`), размер ограничен;
- `api/map.php` отдаёт файлы только из `maps/` и `data/mapres/`: путь и имя
  проверяются (`..`, абсолютные пути и подмена расширения отклоняются), итоговый
  файл обязан остаться внутри каталога-источника, ответ кешируется по ETag;
- карта доступна администратору и гостю, у которого открыта хотя бы одна вкладка
  с координатами; данные читаются только из БД и файлов, записи нет.

### Сборка CSS

Tailwind поставляется локально в `editor-core/tailwind.css` (файл хранится в Git).
Node.js на сервере не требуется. После изменения классов в HTML/JS выполните
из каталога `web-tools/editor-studio`: `npm ci && npm run build:css`.
Конфигурация темы и forms-плагина: `tailwind.config.cjs`.

### Проверки

- `npm test` — тесты ядра и страниц на `node:test` (`tests/*.test.cjs`), в том числе
  `tests/value-comparison.test.cjs` (правило «NULL = '' = 0 = без изменений» в черновике
  гостя, в правке запроса и при сохранении формы).
- `node tools/check.mjs` — синтаксис модулей, правила проекта и языки: проверяет
  `localization/*.js` (манифест ↔ файлы, код и `locale` языка, кириллица в ключах),
  падает на английской строке интерфейса без русского перевода и на русском
  тексте в источнике.
- `tests/i18n-ui-strings.test.cjs` — языковая система целиком: манифест и файлы
  языков согласованы, английский — источник и по умолчанию, в словаре нет русских
  ключей и пустых переводов, подстановки `{0}`/`{1}` совпадают с оригиналом,
  в разметке и коде не осталось русского текста.
- `tests/i18n-roundtrip.test.cjs` — переключение EN→RU→EN: каждая подпись
  переводится и возвращается к источнику, включая составные строки, шаблоны,
  подставленные значения и числительные.
- `node tools/i18n-audit.mjs <страницы>` — прогон отрисованных страниц в jsdom в
  двух режимах: в EN ищет кириллицу, в RU — подписи, которые остались английскими,
  и показывает, сколько подписей вообще отрисовалось (0/0 — страница не
  построилась, проверка пустая). jsdom ставится отдельно:
  `npm install --no-save jsdom`.
- `node tests/php-harness.mjs` — PHP-проверки без живого сервера: `token_get_all()`
  по всем файлам `api/` (синтаксис) и таблица сравнения значений. Нужен пакет
  `php-wasm` (`npm install --no-save php-wasm`); без него проверка пропускается.
- `tests/guest-navigation.test.cjs` — ссылки «открыть запись» (режимы request/guest),
  переход по `?record=&field=` и отмена одного поля в черновике гостя.
