# Синхронизация между базами данных

## Обзор

Модуль синхронизации позволяет безопасно применять изменения из одной базы данных в другую. Все CRUD-операции (создание, обновление, удаление) автоматически записываются в историю изменений и могут быть применены в целевую БД после проверки совместимости структур.

## Архитектура

### Компоненты

1. **`api/db-sync.php`** — серверный API:
   - Сравнение структур БД (schema comparison)
   - Безопасное применение операций в целевую БД
   - Управление профилями подключений
   - Валидация и транзакции

2. **`editor-core/db-sync.js`** — клиентский модуль:
   - Запись истории изменений в localStorage
   - UI для кнопки синхронизации и модалки
   - API для взаимодействия с сервером

3. **Интеграция в `db-crud.js`** — автоматическая запись всех CRUD-операций

4. **CSS стили в `editor-theme.css`** — UI компоненты синхронизации

## Использование

### 1. Настройка целевого подключения

Перейдите в **Настройки** → раздел **Синхронизация между БД**:

1. Нажмите **«Добавить профиль»**
2. Заполните параметры подключения к целевой БД:
   - Название профиля (например, "Production DB")
   - Host, Port, Database, User, Password
3. Отметьте **«Сделать целевым подключением»**
4. Нажмите **«Сохранить и проверить»**

Система автоматически проверит подключение и сохранит профиль.

### 2. Работа в редакторах

Все изменения в любом редакторе автоматически записываются в историю:

- **Создание записи** → операция `create`
- **Обновление записи** → операция `update`
- **Удаление записи** → операция `delete`

Кнопка **«Синхро»** с badge (количество неприменённых операций) появляется в toolbar каждого редактора.

### 3. Применение изменений

1. Нажмите кнопку **«Синхро»** в любом редакторе
2. Проверьте информацию о целевом подключении
3. Нажмите **«Проверить структуру»** для сравнения схем БД
4. Если структуры совместимы — введите **«Применить»** в поле подтверждения
5. Нажмите **«Применить в {название подключения}»**

## Безопасность

### Проверка структур (Schema Comparison)

Перед применением изменений система сравнивает структуры БД:

- **Наличие таблиц** — все таблицы из whitelist должны существовать в целевой БД
- **Совместимость колонок** — типы данных должны быть совместимы
- **Первичные ключи** — PK должны совпадать
- **Nullable** — проверяется совместимость NULL/NOT NULL

#### Уровни проблем:

- **Critical** — несовместимость, применение невозможно
  - Отсутствие таблицы
  - Отсутствие колонки
  - Несовместимый тип данных

- **Warning** — предупреждение, применение возможно
  - Разный размер типа (varchar(100) vs varchar(255))
  - Различия в nullable
  - Различия в PK

### Валидация операций

Все операции валидируются перед выполнением:

- **Whitelist ресурсов** — только разрешённые таблицы
- **Whitelist колонок** — только разрешённые поля
- **Типы данных** — проверка и нормализация
- **ID записей** — валидация для update/delete

### Транзакции

Все операции выполняются в одной транзакции:

- Если **все операции успешны** → commit
- Если **хотя бы одна операция провалилась** → rollback всех изменений

Это гарантирует атомарность — либо все изменения применяются, либо ни одно.

### Подтверждение

Для применения изменений требуется ввести фразу **«Применить»** (или **«APPLY»**).

Это защищает от случайного применения изменений.

## История изменений

### Хранение

История хранится в `localStorage` браузера:

- Ключ: `es_sync_history`
- Максимум: 500 записей
- Формат: JSON массив операций

### Структура записи

```javascript
{
  id: "unique_id",
  resource: "items",           // название ресурса
  action: "update",            // create | update | delete
  data: { ... },               // данные операции (для create/update)
  record_id: 42,               // ID записи (для update/delete)
  label: "Обновление items #42",
  timestamp: 1696700000000,    // время операции
  applied: false,              // применена ли операция
  applied_at: null             // время применения
}
```

### Управление историей

В модалке синхронизации можно:

- **Просмотреть** все неприменённые операции (сгруппированы по ресурсам)
- **Удалить** отдельные операции из очереди (кнопка ✕)
- **Очистить** всю историю (кнопка «Очистить историю»)

После успешного применения операции автоматически помечаются как `applied: true`.

## API Reference

### Клиентский API (`EditorCore.Sync`)

```javascript
// Записать операцию
Sync.record(resource, action, { id, data, label })

// Получить историю
Sync.getHistory()

// Получить неприменённые операции
Sync.getUnappliedOperations()
Sync.getUnappliedCount()

// Пометить как применённые
Sync.markAsApplied(entryIds)

// Очистить историю
Sync.clearHistory({ onlyApplied: false })

// Удалить записи
Sync.removeEntries(entryIds)

// UI
Sync.mountSyncButton(container, { editorName })
Sync.openSyncModal({ editorName })
Sync.updateAllBadges()

// API вызовы
Sync.listProfiles()
Sync.getTarget()
Sync.saveTarget(payload)
Sync.compareSchema({ targetProfileId })
Sync.applyOperations({ operations, targetProfileId, confirmPhrase })
```

### Серверный API (`api/db-sync.php`)

#### `GET ?action=list_profiles`
Возвращает список профилей синхронизации (без паролей).

#### `POST ?action=save_target`
Сохраняет/обновляет профиль целевого подключения.

```json
{
  "profile_id": "abc123",
  "profile_name": "Production",
  "host": "192.168.1.100",
  "port": 3306,
  "database": "mmorpg_prod",
  "user": "root",
  "password": "secret",
  "set_as_target": true
}
```

#### `POST ?action=get_target`
Возвращает текущий целевой профиль.

#### `POST ?action=compare_schema`
Сравнивает структуры исходной и целевой БД.

```json
{
  "target_profile_id": "abc123"
}
```

Возвращает:
```json
{
  "ok": true,
  "comparison": {
    "compatible": true,
    "issues": [...],
    "tables_ok": ["tw_items_list", ...],
    "tables_missing": [],
    "tables_mismatch": []
  }
}
```

#### `POST ?action=apply_operations`
Применяет операции в целевую БД.

```json
{
  "operations": [
    { "action": "create", "resource": "items", "data": {...} },
    { "action": "update", "resource": "items", "id": 42, "data": {...} },
    { "action": "delete", "resource": "items", "id": 43 }
  ],
  "target_profile_id": "abc123",
  "confirm_phrase": "Применить"
}
```

Возвращает:
```json
{
  "ok": true,
  "results": [...],
  "success": 3,
  "failed": 0,
  "committed": true
}
```

## Ограничения

- **Максимум 1000 операций** за одно применение
- **История хранится локально** — при очистке localStorage история теряется
- **Только whitelisted таблицы** — нельзя синхронизировать произвольные таблицы
- **Требуется совместимость схем** — нельзя применить изменения в БД с другой структурой

## Troubleshooting

### «Целевая БД не настроена»
→ Перейдите в Настройки → Синхронизация и добавьте профиль.

### «Структуры несовместимы»
→ Целевая БД имеет другую схему. Обновите структуру целевой БД или используйте дамп из исходной БД.

### «Требуется подтверждение»
→ Введите фразу **«Применить»** в поле подтверждения.

### «Превышено время ожидания»
→ Увеличьте `FETCH_TIMEOUT_MS` в `db-sync.js` или проверьте сетевое подключение.

### Операции не записываются
→ Проверьте, что `db-sync.js` загружается после `db-crud.js` в `page-loader.js`.

## Примеры использования

### Сценарий 1: Разработка → Production

1. Разработчик вносит изменения в локальную БД через редакторы
2. Все изменения автоматически записываются в историю
3. Перед релизом разработчик настраивает подключение к Production БД
4. Проверяет совместимость структур
5. Применяет все накопленные изменения в Production

### Сценарий 2: Тестирование на staging

1. Копируем Production БД на staging
2. Тестируем изменения в редакторах на staging
3. Если всё OK — применяем те же изменения в Production через синхронизацию

### Сценарий 3: Откат изменений

1. Если изменения привели к проблемам — используем дамп БД для восстановления
2. Очищаем историю синхронизации
3. Начинаем заново
