# Editor Studio — безопасность

Короткая модель угроз, список принятых мер и чек-лист развёртывания.
Детали реализации — в `STRUCTURE.md` и в коде (`api/db-core.php` — точка входа).

## Модель угроз

- **Администратор доверенный.** Он имеет полный доступ к игровой БД через студию;
  защита строится вокруг его сессии и пароля, а не против него самого.
- **Гость недоверенный.** Гостевой аккаунт может принадлежать постороннему человеку.
  Гость никогда не пишет в игровую БД: его правки живут в черновике браузера и
  уходят администратору запросом; применяет их только администратор
  (`cr_apply()`, одна транзакция). Доступные гостю вкладки задаёт администратор,
  сервер проверяет тот же список на каждом эндпоинте независимо от UI.
- **Сеть может быть враждебной**: чужие сайты (CSRF), перебор паролей, подделка
  заголовков прокси, кража/фиксация сессии, спам запросами и сообщениями.

## Принятые меры

### Аутентификация и сессии

- Пароли — `password_hash`/`password_verify` (bcrypt). При входе dummy-verify
  выполняется всегда, поэтому время ответа не выдаёт существование логина;
  устаревшие хеши прозрачно перехешируются.
- Политика паролей гостей: минимум 10 символов, максимум 72 байта (граница
  bcrypt), валидный UTF-8 — `editor_password_policy_error()`. В UI есть
  генератор надёжных паролей.
- Попытки входа ограничиваются счётчиками в SQLite-хранилище (не в сессии):
  по IP и по паре «IP + логин», с `Retry-After`.
- Сессия: idle-timeout 12 часов, абсолютный срок 7 дней (настройки
  `session_idle_seconds` / `session_absolute_seconds`, значения клампятся),
  кука `SameSite=Strict`, `HttpOnly`, `Secure` при HTTPS, `path` сужен до
  каталога студии. ID сессии ротируется при входе, выходе и истечении
  (периодической ротации нет намеренно: параллельные запросы из iframe
  ломали бы друг друга).
- Гостевые сессии инвалидируются версией сессии аккаунта: смена пароля,
  отключение аккаунта, «Завершить сессии» и истечение срока действия
  аккаунта действуют немедленно.

### CSRF и запись

- Каждый POST требует заголовок `X-Editor-CSRF` с токеном сессии
  (synchronizer token, сравнение `hash_equals`). Токен выдаёт
  `GET api/auth.php?action=csrf` и ответы status/login/logout; ротируется
  при входе и выходе. Клиент (`editor-core/http.js`) кэширует токен в
  `sessionStorage`, при `403 csrf_token` обновляет его и повторяет запрос
  один раз (сервер отклоняет такой запрос до обработки, повтор безопасен).
- Дополнительно запись разрешена только JSON-POST с того же origin
  (`require_same_origin_json_post`). GET-эндпоинты не меняют состояние
  (отметка «прочитано» вынесена в POST `mark_read`).

### Авторизация гостя

- Владение запросом определяется только ID гостевого аккаунта из сессии;
  чужие запросы отвечают 404 без утечки факта существования.
- Серверный whitelist ресурсов по вкладкам аккаунта; гость получает 403
  на любую запись вне системы запросов (`guest_action_guard`).

### Лимиты, идемпотентность, аудит

- Глобальные лимиты (запросов на рассмотрении, кулдаун отправки, операций
  в запросе) можно переопределить на конкретный аккаунт; значения
  нормализуются и клампятся на сервере (`guest_effective_limits()`).
- Частота preview/submit/message ограничена счётчиками в хранилище на
  аккаунт (не на сессию — новая сессия не сбрасывает лимит); ответы 429
  несут `retry_after` и заголовок `Retry-After`.
- Отправка запроса идемпотентна: клиент присылает `idempotency_key`,
  стабильный для текущего состава черновика; повтор (двойной клик,
  потерянный ответ, повтор после кулдауна) возвращает уже созданный
  запрос вместо дубликата (таблица `submit_keys`).
- Журнал аудита (`audit_log`, хранится 5000 записей): входы, изменения
  гостевых аккаунтов, отправка/ревизии/отзыв, решения администратора
  (включая массовые и принудительное применение), смена настроек.
  У администратора — вкладка «Журнал аудита» с поиском.
- Принудительное применение (`force`) поверх изменившейся БД требует
  комментария: он остаётся у гостя и в аудите.

### Сеть и заголовки

- IP клиента: `X-Forwarded-For`/`X-Real-IP` учитываются только если
  `REMOTE_ADDR` входит в доверенные прокси (настройка `trusted_proxies`
  или env `EDITOR_STUDIO_TRUSTED_PROXIES`, по умолчанию список пуст и
  заголовкам не верят). Чистая логика — `editor_resolve_client_ip()`.
- CSP на страницах (meta) и в `apache-config.conf`: `default-src 'self'`,
  иконки и библиотеки локальные (`vendor/`), шрифты системные —
  веб-шрифты не загружаются, внешних источников нет. Плюс `nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options:
  SAMEORIGIN`, `Permissions-Policy`.
- Ошибки клиенту отдаются через `editor_safe_message()`: SQL-подробности
  и стеки не утекают, детали пишутся в журнал сервера. У ошибок API есть
  стабильные поля `code` (например, `csrf_token`, `session_expired`).

## Известные ограничения

- CSP содержит `'unsafe-inline'` для скриптов и стилей: страницы редакторов
  используют инлайн-код, поэтому строгий nonce-режим пока недоступен.
  Компенсация — последовательное экранирование вывода (`esc()`) и запрет
  внешних источников.
- Черновик гостя хранится в `localStorage` браузера в открытом виде.
  На общем компьютере гость должен выходить из аккаунта; для переноса
  черновика есть экспорт в файл.
- `Secure` у сессионной куки выставляется, когда PHP видит HTTPS. За
  TLS-терминирующим прокси убедитесь, что PHP получает `HTTPS=on`
  (например, через `fastcgi_param HTTPS on`), иначе кука уйдёт без флага.

## Чек-лист развёртывания

1. **HTTPS обязателен** вне localhost: пароль администратора и сессионная
   кука не должны ходить открытым текстом. За прокси — см. ограничение
   про `Secure` выше; HSTS-заголовок заготовлен в `apache-config.conf`.
2. **Пароль администратора** задаётся при инициализации
   (`php tools/init-db.php --password=…`); без пароля вход закрыт.
3. **`data/` недоступна снаружи**: в каталоге лежат SQLite-база студии и
   конфиги. Проверьте, что веб-сервер отдаёт 403/404 на
   `data/editor-studio.sqlite` и `data/db-config.json`
   (правила есть в `apache-config.conf`).
4. **Прокси**: если студия стоит за обратным прокси и нужны реальные IP
   в аудите/лимитах, перечислите прокси в `trusted_proxies` настройкой
   или env `EDITOR_STUDIO_TRUSTED_PROXIES=10.0.0.0/8,...`. Не доверяйте
   заголовкам «на всякий случай» — пустой список безопаснее.
5. **Гостевой доступ** выключен общим переключателем, если гости не нужны;
   аккаунтам выдавайте минимальные вкладки, срок действия и индивидуальные
   лимиты. Удалённые/отключённые аккаунты теряют доступ немедленно.
6. **PHP**: `display_errors=Off`, `log_errors=On` в проде; `pdo_sqlite`
   включён; каталог `data/` доступен на запись только пользователю PHP.
7. **Бэкап**: `data/editor-studio.sqlite` (+ `-wal`/`-shm` при горячем
   копировании) — в нём аккаунты, запросы и аудит. Игровая БД бэкапится
   отдельно (вкладка «Database»).
8. **Перед обновлением** прогоняйте проверки из папки студии:
   `npm test`, `node tools/check.mjs`, `node tests/php-harness.mjs`.

## Сообщить о проблеме

Нашли уязвимость — не публикуйте детали до исправления: напишите
администратору сервера напрямую, приложив шаги воспроизведения и,
если есть, записи из журнала аудита вокруг инцидента.
