# Achievements: анализ и план упрощения архитектуры

Документ описывает текущее состояние системы достижений (по состоянию на ветку
`arena/851cbd43-teeworlds-mrpg-0-6`, коммит `472a6d5`) и предлагает план
рефакторинга **без изменения набора функций**: новые сервисы, интерфейсы и
слои абстракций не вводятся.

Охват: `achievement_manager.{h,cpp}`, `achievement_data.{h,cpp}`,
`achievement_listener.{h,cpp}`, `achievement_db.{h,cpp}`, интеграция с
`account_data.{h,cpp}` / `account_db.{h,cpp}`, схемы `mrpg_shared.sql`.

---

## 1. Как система устроена сейчас

### Данные

- `tw_achievements` — 152 статических описания, 11 типов (`AchievementType`),
  58 цепочек по паре `(Type, Criteria)`. Уровни цепочки — строки с одним и тем же
  `(Type, Criteria)` и возрастающим `Required`.
- `tw_accounts_achievements` — по одной строке на цепочку на аккаунт:
  `(AccountID, AchievementType, Criteria, Progress, CompletedLevel)`.
  `CompletedLevel` хранит **ID achievement-а**, а не номер уровня.

### Потоки

1. **Старт сервера.** `CAchievementManager::OnPreInit()` (`achievement_manager.cpp:140`)
   делает `SELECT * FROM tw_achievements`, создаёт `CAchievementInfo` в
   `MultiworldIdentifiableData<std::deque<...>>`, затем сортирует все описания
   **по имени**. `OnPreInit()` вызывается только в initializer-мире, поэтому
   дублирования описаний при многомировом запуске нет.
2. **Логин.** `CAccountData::Init()` → `InitAchievements()`
   (`account_data.cpp:254`) создаёт по `CAchievement` на описание и запоминает
   их **дважды**: в `CAchievement::Data()[ClientID]` (deque) и в
   `CAccountData::m_apAchievements` (map по ID). Далее асинхронный этап
   `LoadAchievementsProgress()` (`account_data.cpp:267`) читает строки прогресса,
   группирует их по `(Type, Criteria)` и инициализирует каждый `CAchievement`.
3. **События.** `CAchievementListener` подписан на 7 событий. Общий
   `UpdateAchievement()` (`achievement_listener.cpp:73`) проходит по **всем**
   achievement-ам игрока, отбирает совпавшие по типу и criteria и вызывает
   `CAchievement::UpdateProgress()`. Тот меняет прогресс, проверяет завершение,
   выдает награду и троттлит запись в БД раз в 5 секунд.
4. **Меню.** `ShowMenu()` (`achievement_manager.cpp:201`) считает 4 счётчика
   отдельными проходами. `ShowTypeList()` (`achievement_manager.cpp:236`) на
   каждое открытие заново строит `map` цепочек, `unordered_map` уровней и
   `unordered_set` видимых элементов, после чего `AddAchievementDetails()`
   вторым switch-ом по типу форматирует текст цели и награды.
5. **Сброс клиента.** `OnClientReset()` (`achievement_manager.cpp:166`) освобождает
   `CAchievement::Data()[ClientID]`.

Итого в каталоге `achievements/` — 845 строк, из них ~392 строки — менеджер.

## 2. Найденные проблемы

Обозначения: **P0** — ошибка поведения/данных, **P1** — дублирование и
неэффективность, **P2** — мёртвый код и косметика.

### P0. Ошибки, которые стоит вынести в отдельное согласие на изменение поведения

| # | Где | Проблема |
|---|-----|----------|
| 1 | `achievement_data.cpp:78` + `mrpg_shared.sql` (тип 10, ID 142/143/144) | У всех трёх достижений `CompleteQuest` в БД `Required = 0`. `UpdateProgress()` делает `clamp(progress, 0, 0)` → прогресс всегда 0, а `CAchievementInfo::IsCompleted()` (`achievement_data.cpp:30-32`) требует `progress > 0`. **Квест-достижения не завершаются в рантайме.** Это не стилистика: для `Equip` тот же switch работает только потому, что `Required = 1`. |
| 2 | `account_data.cpp:303` | При загрузке `Completed = CompletedLevel >= ID || ClampedProgress >= Required`. Для `Required = 0` второе условие истинно при любом наличии строки → achievement помечается выполненным после релогина даже с `Progress = 0, CompletedLevel = 0`. Прямое противоречие с правилом завершения в п. 1. |
| 3 | `account_db.cpp:451-458` + `achievement_listener.cpp:73-91` | Все уровни цепочки пишут **одну и ту же строку** БД, но каждый клампит прогресс к своему `Required`. Итоговое значение зависит от порядка обхода. Пример из реальных данных: цепочка `(9, 2)` — ID 109 `Required=1` («Hard-earned iron») и ID 114 `Required=500` («Blacksmith»). `CAchievementInfo::Data()` отсортирован по имени, поэтому «Blacksmith» пишется раньше и значение 500 перезаписывается единицей. Дополнительно `db_async.h` явно говорит, что порядок отправки запросов не гарантирует порядок коммита, а SQL использует обычное `Progress = ?`. Для accumulate-цепочек возможна потеря прогресса и при гонке запросов. |

### Отдельно про скорость

Проблема 5 (152 итерации на событие) в абсолютных числах небольшая: это
десятки тысяч простых сравнений в секунду даже в бою. Индекс по `(Type, Criteria)`
уменьшит её до 1–14 итераций, но это **оптимизация по профилировку**, а не
необходимое условие упрощения. Проблема 6 проявляется только при открытии меню
и тоже не критична; там важнее убрать три вспомогательных контейнера, а не
само выделение памяти.

## 3. Минимальная целевая архитектура

Сохраняем четыре существующие роли и не добавляем пятой:

```
tw_achievements ──(OnPreInit, 1 раз)──> CAchievementInfo::Data()   // только описания
                                             │
        ┌────────────────────────────────────┼─────────────────────────────┐
        │                                    │                             │
CAchievementListener                 CAccountData (load stage)      CAchievementManager
  (7 адаптеров событий,                 (только загрузка            (только меню и инициализация)
   один общий Update)                   прогресса из БД)                   │
        │                                    │                             │
        └──────────> CAchievement::Data()[ClientID] <───────────────────────┘
                     (единственный владелец рантайм-состояния)
                                    │
                          AchievementDb::SaveProgress()
```

Правила целевой архитектуры:

1. **Один владелец рантайм-состояния.** `CAchievement::Data()[ClientID]`;
   `CAccountData::m_apAchievements` удаляется. Порядок deque остаётся порядком
   `CAchievementInfo::Data()` — от него неявно зависят индексный поиск и порядок
   выдачи наград.
2. **Один источник правил завершения.** `CAchievementInfo::IsProgressEnough()`
   (маленький метод того же класса) используется и в рантайме, и при загрузке
   из БД. Сейчас правило продублировано switch-ом в `IsCompleted()` и выражением
   `ClampedProgress >= Required` в `account_data.cpp`.
3. **Один владелец SQL достижений.** `AchievementDb`: `ListAchievements()`,
   `LoadProgress()`, `SaveProgress()`.
4. **Одна точка записи на цепочку.** Записывает только последний уровень
   цепочки (`m_bIsChainTail`), он же хранит «сырой» прогресс. Остальные уровни
   в БД не пишут.
5. **Никаких новых интерфейсов/сервисов/DTO/репозиториев.** `CAchievement`,
   `CAchievementInfo`, `CAchievementListener`, `CAchievementManager`,
   `AchievementDb` остаются теми же пятью сущностями.

Сокращение кода ожидается примерно на 80–120 строк в основном за счёт удаления
трёх помощников меню, четырёх счётчиков и pass-through метода.

## 4. План рефакторинга

Шаги идут по возрастанию риска. Шаги 1–3 сохраняют текущее наблюдаемое
поведение (включая баги). Шаг 4 убирает дублирование правила завершения и
попутно исправляет баг №2 — без этого объединить правила завершения нельзя. Шаг 5 —
остальные исправления, требующие отдельного решения.

### Шаг 0. Зафиксировать поведение (до правок)

- Снять скриншоты/текстовый дамп всех 11 групп меню и list-меню для тестового
  аккаунта с частично выполненными цепочками (в том числе `(9, 2)` и `(11, 0..6)`).
- Снять строки `tw_accounts_achievements` этого аккаунта до и после набора
  прогресса, релогина и выхода.
- Добавить тесты в существующий harness `src/test/db_account.cpp` (scripted
  driver) на `SaveProgress`: проверка bound-параметров и монотонного `Progress`.
  Отдельно — тест правила загрузки для `Required = 0` и `CompletedLevel >= ID`.

### Шаг 1. Убрать вторую коллекцию и мёртвый код (чисто механически)

1. Удалить `CAccountData::m_apAchievements` (`account_data.h:40`).
2. `InitAchievements()` (`account_data.cpp:254`) создаёт элементы напрямую в
   `CAchievement::Data()[ClientID]`, в том же порядке, что и описания.
3. `LoadAchievementsProgress()` (`account_data.cpp:292-306`) идёт по
   `CAchievement::Data()[ClientID]`, получает ID через `pRuntime->Info()->GetID()`
   и вызываёт `Init()` на самом объекте. Map по ID больше не нужен.
4. Удалить `WasCompleted`, `CompletionChanged`, `m_LastSavedProgress`,
   `m_LastSavedCompleted` (`achievement_data.*`); оставить `m_LastSaveTick` как
   единственный таймер троттлинга.
5. Убрать повторное присваивание ID в `CreateElement()`, `RewardExists()`,
   неконстантную `GetRewardData()`, `friend class CAchievementManager`.
6. Сделать `ShowMenu()`, `ShowTypeList()`, `AddAchievementDetails()` приватными.

Проверка: меню, награды и строки БД совпадают с baseline.

### Шаг 2. Собрать SQL достижений в одном месте

1. Перенести `LoadAchievements()` и `SaveAchievement()` из `account_db.{h,cpp}`
   в `achievement_db.{h,cpp}`, сохранив текст SQL и bound-параметры.
2. Удалить `CAccountData::UpdateAchievementProgress()` (`account_data.cpp:649`).
   `CAchievement::UpdateProgress()` сам вызывает
   `AchievementDb::SaveProgress(pPlayer->Account()->GetID(), *m_pInfo, ...)`.
3. Заменить `SELECT *` на явный список колонок; использовать существующий
   `TW_ACHIEVEMENTS` или удалить макрос (выбрать одно).
4. Обновить тесты SQL на новый namespace.

Проверка: `LoadAchievements` и `SaveAchievement` вызываются ровно по одному разу
на логин/сохранение; `#include` в `account_data.cpp` сокращаются.

### Шаг 3. Упростить меню без потери порядка вывода

1. Удалить `BuildLevelInfoByAchievement()` и `BuildVisibleAchievements()`
   (`achievement_manager.cpp:65-100`). В `ShowTypeList()` для каждой цепочки:
   - первым проходом найти `lastCompletedIndex`;
   - вторым проходом по `i` выводить элементы `i <= min(lastCompletedIndex + 1, size - 1)`,
     подставляя `Level = i + 1` и `TotalLevels = size`.
   Порядок цепочек (`std::map` по criteria) и внутри цепочки (sort по
   `Required`, затем ID) остаётся прежним — это важно: порядок group `Leveling`
   идёт по criteria-профессий, а не по имени.
2. Удалить четыре метода счётчиков. В `ShowMenu()` одним проходом по
   `CAchievement::Data()[ClientID]` заполнить массивы `total[11]` /
   `completed[11]` и суммы; отрендерить группы из этих массивов.
3. Вынести форматирование награды в `CAchievementInfo`: при `Init()` один раз
   посчитать `m_RewardText` из того же JSON и использовать его в меню.
   `CAchievement::RewardPlayer()` продолжает читать JSON для выдачи.
4. Заменить опасные обращения в `AddAchievementDetails()` на безопасный helper
   `GetGoalText(pInfo)` с fallback-строкой, если описание предмета/квеста/бота
   отсутствует. Убрать «тихую» пустую ветку `CraftItem`.
5. При желании: оставить `BuildAchievementChains()` как есть (он один раз в
   открытие меню) — это дешевле, чем вводить кэшированный индекс цепочек с
   неочевидным временем жизни указателей на `CAchievement`.

Проверка: полное совпадение дампов меню с baseline (кроме п. 4 в случае
отсутствующих описаний).

### Шаг 4. Одна точка записи и введение `IsProgressEnough()`

1. Добавить в `CAchievementInfo` метод `IsProgressEnough(int Progress) const` —
   тот же switch, что сейчас в `IsCompleted()`, но без проверки criteria.
   `IsCompleted()` вызывает его после проверки criteria.
2. Пометить последний уровень каждой цепочки (`m_bIsChainTail`) при загрузке
   описаний в `OnPreInit()`; это одно bool-поле на описание.
3. В `CAchievement::UpdateProgress()` запись в БД делать только для
   `Info()->IsChainTail()`. Логика завершения уровней сохраняется: при
   повторной загрузке более низкие уровни выводятся как выполненные из
   сохранённого прогресса старшего уровня.
4. `account_data.cpp:303` использует
   `Completed = CompletedLevel >= AchievementID || pInfo->IsProgressEnough(ClampedProgress)`.
   Это убирает второе определение правила завершения.
5. Оставить в `SaveProgress` обычное `Progress = ?` — одна точка записи уже
   убирает основную причину регресса из бага №3.

Проверка: тест из шага 0 для цепочки `(9, 2)` показывает 500, а не 1; число
INSERT/UPDATE на серию из 14 событий равно числу затронутых цепочек.

### Шаг 5. Исправления ошибок (изменяют наблюдаемое поведение — нужно отдельное согласие)

1. `CompleteQuest`: считать эффективный `Required = max(Required, 1)` в clamp,
   процентах и правиле завершения. Альтернатива — поправить `Required` на 1 в
   `mrpg_shared.sql` и написать миграцию для живых БД; в рамках рефакторинга
   предпочтительнее код.
2. Исправить условие загрузки для `Required = 0` через тот же
   `IsProgressEnough()`: строка с нулевым прогрессом больше не означает
   «выполнено».
3. Обновить текст цели для квестов: сейчас он показывает `0/0`; после фикса —
   `0/1` (или оставить отображение `0/0`, если так принято в UI).
4. По желанию: индекс `(Type, Criteria)` → список индексов в deque для
   `CAchievementListener::UpdateAchievement()`, если профилирование покажет,
   что 152 сравнения на удар ощутимы. Индекс строится один раз в `OnPreInit()`
   и содержит только `int`, не указатели на рантайм-объекты.
5. Монотонность `GREATEST(Progress, ?)` в `SaveProgress` как страховка от
   переупорядочивания асинхронных запросов. Оговорка: для абсолютных типов
   (`HaveItem`, `Leveling`, `Equip`) БД будет хранить пик прогресса, а не текущее
   значение; это изменение семантики, а не просто рефакторинг.
6. По желанию: сброс отложенного прогресса на выходе. Требует нового хука и
   выходит за рамки «упрощения без новых абстракций».

## 5. Контрольный список приёмки

- [ ] Все 11 групп меню показывают те же счётчики и тот же порядок цепочек.
- [ ] Видимость уровней («выполненные + следующий») не изменилась.
- [ ] Награда за каждый уровень цепочки выдаётся один раз, в том числе когда
      несколько уровней закрываются одним событием.
- [ ] После релогина выполненные achievement-ы остаются выполненными, а
      незавершённые — нет (особенно `CompleteQuest`).
- [ ] Строка прогресса цепочки `(9, 2)` достигает 500, а не обнуляется до 1.
- [ ] Прогресс не откатывается при быстрых последовательных событиях и
      загруженной БД.
- [ ] Нет утечек/висячих указателей после `OnClientReset()` и повторного логина
      на том же ClientID.
- [ ] Сборка и существующий test runner (`run_tests` / `ctest`) проходят.

## 6. Что сознательно НЕ делается

- Не вводятся `IAchievementService`, repository, facade, DTO, шина событий.
- Не меняется схема БД и формат `CompletedLevel` (ID как номер уровня) — это
  отдельная задача с миграцией.
- Не переписывается `GetAchievementTypeName()` и перечисление `AchievementType`:
  они уже просты и используются повсеместно.
- Не трогается система меню `VoteWrapper` за пределами achievement-кода.
- Не добавляется кэш цепочек с указателями на `CAchievement`: время жизни этих
  указателей привязано к ClientID и сейчас корректно управляется только
  `OnClientReset()`.

## 7. Фактически реализованный вариант

Код приведён к описанной архитектуре с несколькими уточнениями:

- Рантайм-контейнер — `std::map<int, std::map<int, CAchievement*>>`
  (`ClientID → AchievementID → состояние`) вместо deque. Это позволяет слушателю
  переходить сразу к нужному уровню цепочки без перебора всех 152 achievement-ов.
- Индекс `(Type, Criteria) → ID` строится в `CAchievementListener` лениво при
  первом событии: слушатели регистрируются в `CGS::OnInit()` **до** `OnPreInit()`,
  где загружаются описания.
- Описания с `Required == 0` нормализуются к `1` в `CAchievementInfo::Init()`.
  Вместо switch-а по типу осталось одно правило `Progress >= Required`, а
  квест-достижения перестали быть невыполнимыми.
- Цепочки (`BuildChains()`) строятся один раз в `OnPreInit()` и хранятся в
  менеджере. Меню больше не создаёт `map`/`unordered_map`/`unordered_set` на
  каждое открытие; порядок групп и уровней сохранён.
- Текст награды кэшируется в описании; при выдаче награды по-прежнему читается JSON.
- Все SQL-запросы достижений перенесены в `AchievementDb`; запись идёт
  fire-and-forget через асинхронный `Db::Query`, как и раньше.
- Прогресс цепочки пишет только последний уровень — это убирает перезапись
  прогресса младшими уровнями. Завершение младшего уровня сохраняется отдельным
  `SaveCompletedLevel()` без изменения `Progress`: абсолютный прогресс может
  уменьшаться, но выданная награда не должна выдаться повторно после релогина.
  `CompletedLevel` по-прежнему монотонен (`GREATEST`).
- Добавлены тесты SQL достижений в `src/test/db_account.cpp`; `achievement_db.cpp`
  подключён к тестовому таргету в `CMakeLists.txt`.

## 8. Проверка интеграции и исправления

Полный проход по интеграции выявил и устранил ещё четыре проблемы:

1. **Порядок загрузки описаний предметов.** Текст наград сначала строился в
   `CAchievementInfo::Init()` во время `OnPreInit()`, но менеджер достижений
   инициализируется раньше инвентаря — item-награды в меню пропали бы. Теперь
   `BuildRewardText()` вызывается из `CAchievementManager::OnPostInit()`, когда
   все описания уже загружены.
2. **Многомировость.** `m_vChains` был обычным полем менеджера, хотя
   `OnPreInit()` выполняется только в initializer-мире. В остальных мирах меню
   было бы пустым. Контейнер цепочек сделан `static inline`, общим для всех
   менеджеров.
3. **Асинхронный порядок записи.** `SaveProgress()` теперь использует
   `Progress = GREATEST(Progress, ?)` наряду с `CompletedLevel`: все игровые
   события монотонно увеличивают прогресс, поэтому переупорядочивание запросов
   больше не может его откатить.
4. **События до авторизации.** `CAchievementListener::UpdateAchievement()`
   дополнительно проверяет `IsAuthed()`, чтобы не писать строки с AccountID = 0.

Также индекс слушателя защищён флагом `m_IndexBuilt`: при пустой БД он не
перестраивается на каждом событии.

**Что проверено**

- Все изменённые `.cpp` компилируются в режиме `g++ -fsyntax-only` с теми же
  include-путями и precompiled headers, что использует проект.
- Отдельный исполняемый тест чистой логики: нормализация `Required == 0`,
  `MatchesCriteria()` для конкретного и обобщённого criteria, `IsProgressEnough()`,
  форматирование текста награды (в том числе с отсутствующим описанием предмета).
- Тесты SQL в `src/test/db_account.cpp` проверяют явный список колонок,
  привязку параметров и монотонные `Progress`/`CompletedLevel`.
- Пошагово проверены события, загрузка/сохранение, меню и сброс клиента.

**Ограничение проверки:** полный `ctest` и запуск сервера невозможны в песочнице
из-за отсутствующих системных зависимостей (MariaDB, Curl, OpenSSL, GTest).
